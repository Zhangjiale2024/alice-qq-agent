## 三、必须知道的坑（按代价排序）

### 坑1：种子必须固定（代价最大）

GPT-SoVITS 的 seed 默认 -1（随机）。客户端默认也是 -1，而配置里长期没有这个键，
等于每次生成都在随机采样。实测同一配置下：

    时长在 4.54~5.72 秒间摆动（±13%），音调 ±15 Hz

听感就是"语速忽快忽慢、前后像两个人"。**这一条让前面好几轮对比全部失效**——
每次测的都是不同的随机样本，我却拿它当"参考音频好坏"的证据，得出了错误结论。

修法：TTS_CLONE_SEED=42。修后连续两次生成 sha256 完全相同。

### 坑2：不要用 ffmpeg 的 afftdn 降噪

同一个参考只改滤镜，实测：

    滤镜              平坦度     频谱质心
    原始不处理        0.1614     4611 Hz
    仅高通            0.1620     4653 Hz
    高通+轻降噪       0.1960     4370 Hz
    我最初那套        0.2044     3894 Hz

afftdn 会留下"音乐噪声"（孤立谱峰），**平坦度反而升高**；
lowpass 把质心砍低 16%，声音发闷。这就是用户说"降噪后完全变了"的原因。

### 坑3：选参考片段不能只看音调

最初按 F0 选，选到 BV14v4y1e7QC 第 32 秒那段（F0 526 Hz），
但同一视频里最干净片段的**频谱平坦度是 0.054，那段是 0.1614（3 倍差）**——
那段混了背景音，是"沙哑、噪声多"的来源。

选片段要同时看：F0 高 + 平坦度低。当前用同视频第 304 秒片段（F0 415、平坦度 0.0629）。

### 坑4：换参考时一次只改一个变量

上面那个问题难定位，就是因为我**同时换了源视频和降噪**，"声音变了"无法归因。

### 坑5：别让间接指标代替耳朵

平坦度、MFCC 距离、F0 这些**只能证伪，不能证成**。多次出现"指标改善但听感更差"。
指标用来快速筛掉明显不合格的，**最终判断必须靠听**。

### 坑6：错误报告要具体

"不太对""变了"这类描述我只能盲试，浪费好几轮。
具体症状（"忽快忽慢""有电流声""第二句音调跳了"）我能直接定位。

### 坑7：PowerShell 脚本的三个陷阱

1. **.ps1 必须带 UTF-8 BOM** —— 否则 PowerShell 5.1 按 GBK 读，中文被拆坏，
   汉字某个字节正好是引号就会截断字符串，报一堆莫名语法错误
2. **别用反引号续行** —— 写进别的工具容易被当转义符
3. **路径里的反斜杠要注意转义** —— 我用普通模板字符串写 "D:\DSHWORK\..." 时
   反斜杠被吃掉，变成了 "D:DSHWORK..."，导致脚本静默读不到 .env

### 坑8：改网络调用要同步改测试打桩点

代码从 urllib.request.urlopen 换成 net.open 后，
原来打桩 aliceqq.X.urllib.request.urlopen 的测试**拦截失效、真的发网络请求、套件卡死**。
已全部改成打桩 aliceqq.X.net.open（19 处）。

### 坑9：GPT-SoVITS 服务会静默降级

服务没起时 TTS_FALLBACK=baidu 会让声音**换成百度**，而 ok=True、error 为空。
已加降级提示（按用户 30 分钟限频）。

### 坑10：模型目录缺 config.json 会导致静音

只下 pytorch_model.bin 而缺 config.json 时，transformers 按默认配置（BERT-base 768 维）
建模型，而权重是 roberta-large（1024 维），维度不匹配整条推理链崩掉、
**只输出 1 秒静音**，且加载时不报错。补上 config.json 立刻恢复。

### 坑14：整数秒切片必然切到字（2026-10-09 实证）

参考片段 `same4` = `refs\ja_full.wav` 的 **304.000~312.000 秒**（互相关验证，
相关系数 1.0000）。但那句台词的**"先生"起音在 303.69 秒**——
整数秒起点比真正的词起点晚了 0.31 秒，正好把"先"字的起音切掉。
后果：whisper 把首字听成别的音（`女性の人生初の…` 而非 `先生の人生初の…`）。

正确做法是**对齐语音边界 + 首尾强制补数字静音**：

    片段起点 = 有声起点 − 0.25s，终点 = 有声终点 + 0.25s
    再在首尾补 0.15~0.20 秒**真正的零值**静音

**只靠能量阈值对齐不够**：这段音频有背景音乐，句首音乐渐入被当成静音，
8 个候选的起始余量全是 0.000 秒，等于又切了一次。必须补真静音。

### 坑15：B站搜索要 WBI 签名，且未登录也会返回 wbi_img

搜索接口 `x/web-interface/search/type` 不带签名会 **412**。
签名要 WBI（img_key+sub_key → mixin_key → md5）。

**最容易踩的一点**：未登录时 `x/web-interface/nav` 返回
`code=-101 账号未登录`，但 `data.wbi_img` **照样有值**。
按 `code==0` 判断就永远取不到 key。可复用实现见
`GPT-SoVITS-setup\bili_api.py`。

顺带查出：**`.env` 里的 `BILIBILI_SESSDATA` 是假的占位值**（34 字符，
真实值 60~80 字符），所以下载到的音频一直是最低码率档。

### 坑16："指标完美"的静音窗口

按"频谱平坦度越低越干净"筛片段，会选出**平坦度 0.0022** 的片段——
而语音的平坦度通常是 0.02~0.1。那些片段其实是**静音或纯音乐**：
静音没有谱结构，平坦度自然趋近 0。

**筛选指标自己会指向完全错误的答案。** 必须加两道闸门：

    有声占比 >= 0.75（真的有在说话）
    用 ASR 回读合成产物，能还原原文（真的听得懂）

反过来的用法也成立：**换参考后合成响度突然翻倍**
（RMS 0.079 → 0.197）就是"参考里混了非语音成分"的强烈信号。

### 坑17：同源片段能用，换源片段会让合成变乱码

实测 9 个候选参考，固定 text/seed/speed，再把合成产物丢回 ASR：

    同源片段（ja_full 自己的片段）  能还原 12/16 ~ 38/40 字  <- 可用
    ja4 女仆线（指标最干净）        2/16 ~ 34/40 字，多数乱码
    ja3 / ja5 / ja6 换源            2/16 ~ 5/16 字，基本听不懂

即"指标更漂亮"的换源候选，合成出来是**听不懂的中文**。
A 计划里"换更好音源"这条路目前走不通，有效收益只有
"同源换片段 + 修首字"。

### 坑18：PowerShell 管道会杀掉上游长任务

    命令 | Tee-Object 文件 | Select-Object -First 60

`Select-Object -First n` 拿到 n 个对象后会关掉上游管道，
长任务被中途掐死、日志还写不出来（表现像"卡住 10 分钟无输出"）。
诊断脚本一律用 `python -u`（无缓冲）+ 后台作业 + `job_output` 读输出。

## 四、已知特性（不是 bug，别去修）

### 按文本的"首次不同"

同一文本连续合成，第 1 次与之后几次结果不同（字节数一样，内容不同），
第二次起稳定。**这个差异按文本出现**，用别的文本预热消不掉。

好消息：那个"第 1 次"结果本身是确定的（跨服务重启一致），
而 bot 每句话只合成一次，所以用户听到的始终是同一个版本。

### aux_ref_audio_paths 没有权重参数

官方没有权重参数。实测把某段音频在辅助里重复 1/2/3 次，
音色指纹距该参考 0.1150 -> 0.1084 -> 0.1061 -> 0.1054（单调变近），
即**重复有效、方向正确，但不是校准过的比例旋钮**。

### 空 prompt_text 反而更好

空 prompt 走 naive_infer，**完整合成所有切分句**；
有 prompt 走 batch_infer，实测**只合成第一句就停**（5.32s -> 2.04s 截断）。

### 踩的坑

**坑11：模型默认缓存位置在工作区外**

faster-whisper 默认把模型下到 C:\Users\<用户>\.cache\huggingface，
受限环境会报 WinError 5 拒绝访问。必须设 HF_HOME 或传 download_root，
指到**能写的目录**。国内还要设 HF_ENDPOINT=https://hf-mirror.com。

**坑12：本地后端被"缺 key 就关闭"的逻辑误伤**

config.py 原本有：

    if asr.enabled and not asr.api_key:
        asr.enabled = False

本地后端**不需要 API key**，这条会把本地 ASR 一起关掉，
变成"开了 ASR 却永远不可用"。已改成只对云端后端生效——
**TTS 那边犯过一模一样的错**（会把 baidu/google 这类免费 provider 一起关掉）。

**坑13：ctranslate2 找不到 CUDA 运行库（但文件其实已在）**

在 cuda 上加载会报：

    RuntimeError Library cublas64_12.dll is not found or cannot be loaded

而 cublas64_12.dll / cudnn*_9.dll **已经躺在 torch\lib 里**（torch 自带的）。
问题是 Windows 上 Python 3.8+ 不再从 PATH 查找扩展模块的依赖，
必须显式 os.add_dll_directory。

解法：_add_torch_cuda_dlls() 把 torch\lib 加进 DLL 搜索路径。
**不需要另外装 nvidia-cublas-cu12 / nvidia-cudnn-cu12。**

### 10.1 模式改为**按会话隔离**（行为变更，会影响体感）

原先 `/爱丽丝`、`/助手` 是**按用户全局**存的：在 A 群切成助手后，
B 群和私聊都跟着变了。这违反 V5 的群隔离要求。

现在：

    新表 session_mode(user_id, scope, mode)
    scope = 'private'（私聊）或群号

2. **私聊切模式会更新"全局默认"**，所以他第一次去的新群沿用它——

3. 切换后的回复会明确写"只对本群生效"，否则用户会以为全局都切了。

`set_mode()` 保留旧签名（`scope` 默认私聊），所以老调用不用改。
老库升级用 `migrate_profile_modes_to_sessions()` 把 `user_profile.mode`
灌进新表（只处理没有任何会话记录的用户，不覆盖升级后已经切过的）。

## 十一、V5 第二批：群管理（2026-10-09 已完成）

核心是新增 `aliceqq/moderation.py`：**只做判断、不做动作**。动作执行在引擎，
因为要过权限和确认；分开之后判定层可以完全离线测试。

### 12.1 判定分层：不是"能不能识别广告"，而是"不该罚的绝不罚"

误伤正常群友的代价远大于漏掉一条广告，所以判定分三档：

    high    拉群/加微信/电商链接邀请        -> 可进入处罚流程（仍需确认）
    medium  推广词+联系方式、管理员敏感词、重复刷屏 -> 可自动警告
    low     只出现了推广词（如"卖号"）       -> 只记录，绝不处罚

**显式豁免**（`is_never_punish`，永远不构成处罚理由）：

- 批评/吐槽机器人：判据是"主语是机器人（爱丽丝/机器人/bot/AI）
  **且**句子里有负面词"。拆成两个条件是因为把负面词写进一条正则会漏掉
  "这个机器人不太好用"这类中间带修饰词的写法，而穷举修饰词必然漏。
  （实测还踩过一次：我读代码时把"不太好用"看成"不好用"，
  导致词表里没有它、判定直接漏掉。）
- 观点分歧（我觉得/感觉 + 不对/不好）
- 正常求助与提问（为什么/怎么/求助/请问）
- 带正常上下文词的（官方/公告/更新/攻略/角色/开卡…）触发降级

另外：匹配前清理零宽字符（广告常用 `\u200b` 规避），但审计里展示原文；
群主/管理员自己发的消息完全不审。

### 12.2 默认安全策略（V5 第六节逐条落地）

| V5 要求 | 实现 |
|---|---|
| 没有明确权限时不执行管理操作 | 所有管理指令先过 `_is_group_admin` |
| 没有明确规则时不自动处罚 | 默认 `dry_run=True`，命中只记录+提示管理员 |
| 禁言/踢出/批量撤回默认需要确认 | `queue_action()` 对高风险动作建待确认记录 |
| 不得根据记忆/身份/兴趣/观点处罚 | 判定只看当前消息 + 规则，**不读任何用户记忆** |
| 不得因为批评机器人而处罚 | `is_never_punish()` 前置豁免，有 18 条保护性用例 |
| 不得伪造撤回/禁言/踢出成功 | 适配层执行后必须回填 `record_action_result()`，失败写清原因 |
| 操作失败时清楚说明失败原因 | 失败回执带 `detail`（如"机器人不是管理员"） |

## 十三、语音发不出去 / 不是爱丽丝音色（2026-10-09 修复）

用户截图反馈："让它发语音它怎么不会发"。

排查后发现是**两个独立问题叠在一起**，而且都不在"发送"这一环：

### 13.1 语音意图漏判 —— 根本没合成语音

用户那句是「你来唱给我听，把语音发给我」。`Engine._wants_voice()` 返回 **False**，
所以压根没走语音合成。漏判原因是两条模式：

    r"发[^，。！？!?]{0,3}语音"    # 只认【发 → 语音】的顺序
                                   # "把语音发给我"是【语音 → 发】，顺序相反
    没有"唱"这一类               # "唱给我听""唱一首"一条都不认

**后果最坏的一点**：因为没挂媒体，模型就在正文里自己编了
「现在爱丽丝把这段发成语音——启动！」「（语音尝试发送中……）」——
用户看到的是一句永远不会兑现的承诺。

修法：补反向语序模式 + "唱"这一整类请求，并加了 15 条应识别、6 条不应误判的用例。

### 13.2 夹英文就退回百度音色 —— 发出来也不是爱丽丝

意图修好后语音确实发了，但日志里出现
「克隆音色服务没连上，这次先用备用声音念的」。用户听到的是**百度音色**。

根因：用户那句话里有 **"Na~ LiLaBaLiLa~"**。文本一夹英文，GPT-SoVITS 就走
`g2p_en` 做英文转音素，而 `g2p_en` 需要 nltk 的两个资源：

    corpora/cmudict
    taggers/averaged_perceptron_tagger_eng

两个都缺 → 服务端返回 **HTTP 400**（`Resource 'cmudict' not found`）→
前端 `FallbackTTS` 静默换成百度音色。

**为什么这个 bug 特别阴**：`ok=True`、`error=''`，只有一句不显眼的
"（克隆音色服务没连上，这次先用备用声音念的。）"；而且**纯中文完全正常**，
只有夹英文才复现——所以看起来像"偶发"。

修法与踩的坑：

    1. nltk.download() 走 raw.githubusercontent.com ——
       本机**直连超时、走系统代理 11808 也超时**。
    2. cmudict 不用下：GPT-SoVITS 自带的 `GPT_SoVITS\text\cmudict.rep`
       实测就是 **CMUdict 0.7b 纯文本**（134429 行），与 nltk 语料同格式，
       直接装成 nltk 资源即可（脚本 98）。
    3. tagger 本机没有，但 **ghproxy.net 与 cdn.jsdelivr.net 可用**
       （raw 的镜像），从那里下（脚本 99）。
    4. **装完必须重启服务**：`g2p_en` 在 import 阶段就 `cmudict.dict()` 了，
       不重启不生效。

装到 `envs\gptsovits\nltk_data`（本来就在 `nltk.data.path` 里，
且在工作区内——工作区外目录在受限环境下可能写不进去）。

### 13.3 新增护栏：不许编造"已发送媒体"

上面 13.1 暴露的更深问题是：**模型会编造媒体发送结果**。V5 明确禁止。
所以加了 `Engine._strip_media_overclaim()`：媒体挂载完成之后，
如果正文声称发了媒体、而本轮**实际没挂任何媒体**，就把那些句子删掉并如实说明。
有媒体时原样保留；正常陈述（"语音是合成音""歌词背不下来"）不误伤。

### 15.3 安全：先验证再加载（重要习惯）

`.pth` 是 pickle，`torch.load()` 会执行里面的 `__reduce__`——
**等于运行陌生人的代码**。这份模型来自第三方仓库，所以加载前先静态扫：

* `rvc_03_inspect_model.py`：用 `pickletools.genops()` 遍历 opcode，
  只报告引用了什么，不执行任何东西。

结果：`data.pkl` 只引用了

    collections.OrderedDict / torch._utils._rebuild_tensor_v2 / torch.HalfStorage

标准张量结构，无可疑符号。**注意**：静态扫描能拦明显恶意 pickle，
但不能证明绝对安全。

（顺带学到一个事实：PyTorch 1.6+ 的 `.pth` **其实是 zip 容器**
——`data.pkl` + `data/0..N` 张量。所以直接 `pickletools.genops(整个文件)`
会在第一个 opcode 就报 `ValueError`，要先把 `data.pkl` 从 zip 里取出来。）

### 15.4 三个非显然的坑

| # | 现象 | 根因与解法 |
|---|---|---|
| 1 | `load_model` 打印 "Loading..." 后就报 `AttributeError: 'tuple' object has no attribute 'dtype'` | **PyTorch 2.6 起 `torch.load` 默认 `weights_only=True`**，而 RVC 的 config 里带一个 fairseq `Dictionary` 对象，被拒绝加载；下游拿到 tuple 才报错，症状完全不指向真因。解法：`torch.serialization.add_safe_globals([Dictionary])`（`rvc_05_patch_safe_globals.py`）。**不要**改成 `weights_only=False`——那等于允许任意代码执行 |
| 2 | `f0method='rmvpe'` 卡住不出结果 | rmvpe 首次要 **JIT 编译**，CPU 上极慢。改 `f0method='harvest'`（纯 Python 实现，不需要 JIT）先跑通 |
| 3 | 带 `.index` 时进程**静默崩溃**（无异常、无 traceback） | 退出码 `-1073741819` = **0xC0000005 访问违规**。逐段排查确认：`faiss.read_index` 正常，**`index.search()` 一调就崩**——faiss **1.8.0** 在 Windows 上的 bug。升级到 **1.15.1** 后修复。**注意**：升级 faiss 会连带把 numpy 升到 2.2.6，而 fairseq 声明 `numpy<=1.23.5`；实测 fairseq 仍能导入，但要留意后续可能的兼容问题 |

第 3 条的教训：**"静默崩溃"不等于"没报错"**。要看进程退出码——
`-1073741819` 是 Windows 的 `0xC0000005`，一看就知道是原生层崩了，
而不是 Python 逻辑问题。

## 十六、唱歌流水线（2026-10-10，用户试听确认）

### 16.1 成品与链路

用户 A/B 试听后确认 **v3 参数"刚好"**，现已固化成流水线。

    源歌（B 站爱丽丝翻唱）

      -> [2] RVC 音色转换（TendouAlice v2 / crepe / protect 0.5 / index 0.4 / f0up 0）
      -> [3] 高频收敛（>6 kHz -5 dB）+ 增益留余量 + 重采样 44.1 kHz
      -> 成品 mp3（models_shared\rvc_output\*_成品.mp3）

已产出：《World.execute(me)》(91.8s)、《反方向的钟》(117.3s)。

### 16.2 为什么这么调（都有实测依据）

**"哑"的主因是源里的伴奏**，不是模型：

| | 4-10k | F0抖动 | HNR |
|---|---|---|---|
| 源 原混音 | 0.427 | 0.084 | 0.540 |
| 源 分离干声 | 0.465 | 0.074 | **0.761** |
| 旧成品（混音直接转） | **0.643** | **0.186** | 0.515 |
| 干声 + 原参数 | 0.606 | **0.101** | **0.760** |
| 干声 + 抗噪参数 | 0.606 | **0.099** | **0.763** |

换干声让 **HNR 从 0.515 回到 0.760**（与源持平 = 周期性没被破坏），F0 抖动砍半。
比调参数管用得多。

但 4-10k 只降到 0.606，而且试了 `harvest`/`crepe`、`protect` 0.33/0.5、
`index_rate` 0.5/0.4——**都停在 0.60 上下调不动**，说明高频偏亮来自模型本身。
所以加了输出后的温和搁架衰减（6 kHz 以上 −5 dB）。

**一个我自己犯的测量错误，值得记下来**：我一度把"源 44.1 kHz"和"成品 40 kHz"
的高频占比直接对比（我的诊断按 22 kHz 重采样），得出"降了 6%"的结论。
同域重测才发现，40 kHz 下原样是 **0.963**，降 6% 是跨域比较的假象。
**指标对比必须在同一采样率下做。**

### 16.3 已知边界：**超过约 150 秒的歌会崩**

实测：

    91.8 秒   ✅ 成功
    117.3 秒  ✅ 成功
    196 秒    ❌ 两次都在 RVC 转换阶段以 0xC0000005（访问违规）崩溃

原因判断：单次推理的中间张量随音频时长增长，而本机**可用内存只有 4.9 GB / 共 15.8 GB**。
报错信息具有误导性（`'tuple' object has no attribute 'dtype'`），
但同类崩溃在 faiss `search()` 上也出现过——都是内存层的原生崩溃。

**修法（尚未实现）**：分段处理——按 60~90 秒切、逐段转换、再拼接，
段间做短交叉淡化避免接缝爆音。这是 RVC 处理长音频的标准做法。

### 16.4 两个环境必须**分进程**（踩过）

UVR5 和 RVC 属于两个 Python 环境：

    envs\gptsovits    Python 3.11 + CUDA torch   -> 跑 UVR5 分离（90 秒只要 20 秒）
    pythons\310       Python 3.10 + CPU torch + fairseq -> 跑 RVC（隔离环境）

把它们塞进**同一个进程**会以 `0xC0000005` 崩溃（两套 torch/faiss 混在一起）。
所以 `rvc_15_pipeline.py` 用**子进程 + 各自解释器**串起来，每步之间进程完全退出。

### 16.5 脚本清单

    rvc_15_pipeline.py    总流水线（分进程，推荐入口）
    stage_separate.py     阶段1 UVR5 分离（在 gptsovits 环境跑）

## 十七、修 11:14 日志里的两个 bug + 唱歌改成"只做一段"（2026-10-10）

### 17.1 bug 1：`notice.notify.input_status` 也在跑成员变动 handler

日志证据：

    [DEBUG] Running handler Dependent(call=_handle_member_change)

**"对方正在输入"是状态通知，跟成员进出毫无关系**，却每次都进 handler、
跑一遍依赖注入、再静默 return——群里有人打字就刷一轮日志。

原因：我原来只在 handler **内部**做 `isinstance` 判断，事件已经被派发进来了。
正确做法是在**匹配器层**就用 `Rule` 拦掉。现已加 `_is_member_change(event)`
作为 Rule，handler 内再确认一次作双保险。

### 17.2 bug 2：主动关心对无效用户无限重试

日志证据：

    [alice] 主动关心发送失败 10001: ActionFailed(retcode=1200) 无法获取用户信息
    [alice] 主动关心发送失败 10002: ActionFailed(retcode=1200) 无法获取用户信息

`10001` / `10002` 是 `README` 和 `.env.example` 里的**示例用户**——
开发时用 `--user 10001` 试过，于是档案进了库、`message_count > 0`，
主动关心就把它当真实用户反复重试。为什么这个 bug 会自己冒出来：
`.env` 里曾经把 `PROACTIVE_ENABLED` 打开，调度器一跑就中招。

两层修复：

2. `proactive.mark_failed()` + 24 小时退避：
   发送失败就记下来，一天内不再重试同一个用户。
   没有这个退避，默认 15 分钟一轮 = 一天撞 96 次，而失败原因往往是**永久的**。

### 17.3 唱歌改成"只做一段"（用户要求：不超过一分钟）

用户明确说"只要唱一两段就行，不超过一分钟"。这正好绕开了原来的内存阻塞：

* QQ 语音本身有长度限制，一分钟内最稳；
* 等待时间从 4.6 分钟降到 **88 秒**；
* 不用碰长音频处理。

实现要点：`sing.py` 里 `clip_best()` **不是简单取开头**——
前 55 秒往往是人声进之前的前奏。它算 200~4000 Hz（人声能量区）的包络，
用长度 = 目标秒数的滑动窗找**能量最集中**的位置，命中副歌的概率大得多。
实测《虫儿飞》选中的是 125.9~180.9 秒，《反方向的钟》是 53.8~108.8 秒。

### 17.4 真正的坑：整段推理会崩，必须**分段**

这一段先说结论：**RVC 整段推理在这台机器上不可靠，必须分段。**
我一开始误判成"间歇性故障"，因为它有时成功有时失败。实际规律是：

    55 秒的人声，整段推理 **连续三次全部崩**
    退出码 3221225477 = 0xC0000005（访问违规）
    失败点固定：hubert 加载完、crepe 音高提取开始之后

本机可用内存只有约 4.7 GB（共 15.8 GB），单次推理的中间张量随时长增长。
**分段后每段的峰值内存按段长算，而不是总长**，问题消失。

分段尺寸是实测选出来的，不是拍的：

| 段长 | 结果 |
|---|---|
| 整段 | 55 秒连续崩 3 次，不可用 |
| **15 秒** | 稳定，但 55 秒要切 14 段，约 340 秒（分段开销大） |
| **30 秒** | **同样稳定，7 段 / 238.9 秒** ← 选它 |

段间用 0.4 秒线性交叉淡化，避免硬拼产生"咔"声。

**顺带修掉一个自己写的 bug**：第一版拼接把重叠区**整段拼了上去**，
导致 195.79 秒的输入产出 200.72 秒（多 4.93 秒）。改成"每段只贡献新增部分"后，
195.79 -> 195.52 秒（差 0.14%，是逐段整数取整的累积）。

### 17.5 另一个教训：报错信息会把人带偏

崩溃时看到的是：

    AttributeError: 'tuple' object has no attribute 'dtype'
      at scipy/io/wavfile.py:798  dkind = data.dtype.kind

这句**完全不指向真因**。真相是 torch 2.6 的 `weights_only` 拒绝加载 `.pth`，
`self.cpt` 变成 tuple，一路传到 `wavfile.write` 才炸。
现在 `stage_convert.py` 在生成后**校验产物真的是音频**
（`sf.info` + 时长 > 0），让错误在源头就变成一句能看懂的话。

### 17.6 现在的状态

    点歌 -> 出成品：  sing.py "歌名"，约 88 秒
    产物：            models_shared\rvc_output\sing_<BV>_成品.mp3（约 1.3 MB / 55 秒）
    稳定性：          55 秒片段连续多次成功；整段推理已知会崩，已不采用

**还没接进 bot**：目前是从命令行跑。要在 QQ 里点歌，还需要把 `sing.py`

## 十八、缩到 30 秒 + 挖出真正的崩溃根因（2026-10-10）

用户要求"缩到 30 秒一段，等待降到约 50 秒"。结果：**69.3 秒**，并顺带
挖出了前面所有 `0xC0000005` 崩溃的**真正根因**——不是我的代码。

### 18.1 根因：Windows 页面文件被占满（不是代码 bug）

一直以为是"内存不够/RVC 有 bug"，实际报错最终以最直白的形式出现了：

    ImportError: DLL load failed while importing parselmouth: 页面文件太小，无法完成操作。

查配置：

    提交上限      53.3 GB
    可用虚拟内存   1.7 GB   ← 几乎耗尽
    页面文件      C:\pagefile.sys，已分配 38.4 GB，但 **C 盘只剩 11.3 GB**

凶手（提交内存）：

    dmsvc    （DAMENG 数据库服务）  10.7 GB
    HTGame   （游戏）               10.1 GB
    NTEGame  （游戏）                0.5 GB

**游戏关掉后，可用虚拟内存从 1.7 GB 回到 13.6 GB**，同样的转换立刻正常。
所以整个第十六~十七节里那些"间歇性崩溃""长音频会崩"的现象，
本质上是**当时的虚拟内存余量**决定的，不是音频长度。

**代价**：C 盘只剩 11 GB，页面文件已经扩不动了。彻底解决要
**把页面文件挪到 D 盘**（D 盘有 58 GB 空闲）——那是需要管理员权限 + 重启的
系统级改动，我没有擅自做。现在只是"别再同时开两个游戏"。

### 18.2 顺带修掉我自己写的一个真 bug：中间产物同名覆盖

现象：30 秒的请求，产出了 **195.66 秒**的成品。

原因：流水线里 `stage_separate` 和 `stage_convert` **用了同一个 tag**，
于是 UVR5 的中间目录是同一个：

    stems\sing_<BV>_HP2_all_vocals\vocal_sing_<BV>.wav_10.wav

同一首歌先跑整首（195.79 秒）、再跑 30 秒片段时，两者写**同名文件**；
而 UVR5 见到同名文件**就跳过重算**，于是转换阶段读到的是上一轮的 195.79 秒干声。
清理前那个目录下确实躺着 195.79 / 55.00 / 30.00 三个互相覆盖的 vocal。

两处修复：

1. **tag 带上输入时长**（`<标签>_<秒数>`），不同输入永不撞名；
2. `stage_convert.py` 增加**输出时长与输入一致性校验**（容差 2 秒）。
   这一条很关键——"读错输入文件"产生的是**合法音频**，
   前面那些"是不是有效音频"的检查全都抓不到它。

### 18.3 最终的 30 秒配置

    sing.py            CLIP_SECONDS = 30.0
    stage_convert.py   CHUNK_SECONDS = 30.0
                       SINGLE_PASS_SECONDS = 40.0   # 30 秒片段走单段，不必切

实测（游戏已关）：

    30.00 秒片段 -> 成品 29.98 秒，总耗时 **69.3 秒**
    分离 10 秒 / 转换 57 秒 / 收敛 2 秒

选段的滑动窗仍按 200~4000 Hz 人声能量找副歌（本次选中 70.5~100.5 秒）。

## 十九、唱歌接进 QQ（2026-10-10）

### 19.1 怎么用

    自然语言：  唱一首 反方向的钟        （在群里需要 @ 或按群规则触发）
    指令：      /唱歌 群青   /唱 打上花火

首次做的歌要等 **60~90 秒**；**同一首歌第二次点是秒回**（走缓存）。

### 19.2 为什么是"先回一句、再发语音"

整条流水线要跑 60~90 秒。如果放在异步 handler 里直接 await，
这 90 秒里机器人对**所有**消息都不响应——这是不能接受的。

所以流程是：

    1. 立刻回："爱丽丝去练一下《X》，稍等一会儿～"
    2. 把重活丢进 asyncio.to_thread（不阻塞事件循环）
    3. 跑完回："练好了，这首《X》送给你～" + 语音

### 19.3 分层：判定在核心，发送在适配层

    aliceqq/singing.py    意图识别 / 缓存 / 任务封装（**纯标准库，可离线测试**）
    adapters/nonebot_...  拿 bot 对象发消息、把成品当 [CQ:record] 发出

这样"要不要唱、唱什么、有没有做过"都能离线测，
而需要 QQ 的那部分（发送）保持很薄。

### 19.4 意图识别：宁可漏判，不要乱唱

一次重活 90 秒 + 吃满 CPU，**误触发的代价比漏判大得多**。
所以只认"明确在点一首具体的歌"，并且只取**动词之后**的内容。

第一版正则太宽，实测漏判：

    我想听你唱《虫儿飞》   -> 抽出 "你唱《虫儿飞"   （把主语也当歌名了）
    爱丽丝唱首歌           -> 抽出 "首歌"

改成"先定位 唱/来一首/点歌，再只看它后面"之后，18 条实测全对。不触发的例子：

    你会唱歌吗 / 唱歌好听吗 / 你唱得真好听 / 推荐点歌 / 有什么歌单
    爱丽丝唱首歌 / 唱一段吧 / 唱首歌来听听 / 能不能唱首歌   ← 没给歌名，不猜

### 19.5 缓存：省掉重复的 90 秒

`SongCache` 用规范化歌名（去空格、转小写）做 key，
所以 `反方向的钟` / ` 反方向的钟 ` 命中同一条。
歌名里的路径分隔符会被替换掉，防止写到缓存目录外面（有测试卡这条）。

## 二十、修 QQ 实测暴露的三个问题（2026-10-10）

第一次真机跑唱歌，截图暴露了三个问题。**这些都是单测抓不到的**——
测试用的歌名都很规范，而用户真实说法里有"出处前缀"和"纠正句"。

### 20.1 问题一：歌名提取错（把整句诗当歌名）

    用户："唱一首蔚蓝档案的《准备出发》"
    机器人回的："爱丽丝去练一下《蔚蓝档案的《准备出发》》"   ← 把出处也当歌名了
    结果放出：《爱丽丝翻唱&钱是万恶之源吗》

两个原因：

1. **"作品名 + 的"前缀没剥**——"蔚蓝档案的"是出处不是歌名；
2. `detect_song` 原来会把**整个后半句**当歌名。

修法：有书名号就**以书名号内容为准**（用户明确标了歌名）；
没书名号才剥前缀 + 填充词。嵌套时取最里层。

### 20.2 问题二：纠正句被当歌名

    用户："让你唱全速向光不是反乌托邦"        ← 在**纠正**机器人
    机器人："爱丽丝去练一下《全速向光不是反乌托邦》"   ← 整句当歌名了

带判断词的句子（不是/不对/应该/换成…）**不是歌名**，应当直接不触发。
已加 `_NOT_A_TITLE` 拦截。

### 20.3 问题三：搜到完全不相干的歌

    点《Memory of Stella》 -> 放出《爱丽丝翻唱-Starlight》
    点《准备出发》         -> 放出《钱是万恶之源吗》

根因：原来的筛选只检查"标题里有没有『爱丽丝』和『翻唱』"，
于是**任何**一首爱丽丝翻唱都能通过——等于随便糊弄一首。
点了歌却唱另一首，比直接说"没找到"更糟。

加了 `_title_matches()`：**标题必须真的是这首歌**。过程中踩了三个坑：

| 坑 | 现象 | 修法 |
|---|---|---|
| 只看"包含" | 点《群青》选中了《群青**信号**》（另一首歌，因为更短排前面） | 看歌名**后面那个字**，是"信/的/之/版/号"之类就判否 |
| 时长上限 240 秒 | 《群青》的**全部**候选都在 246~260 秒 → 报"未找到" | 上限放宽到 420 秒（反正只截 30 秒） |
| 要求标题含"翻唱" | 《AI爱丽丝-群青》这类正经标题被排除 | 放宽为"爱丽丝 + AI/唱"即可 |

**最省事的判法**（试了两种才对）：不要试图"剥掉标题里的出处标记再看剩下的是不是歌名"——
我那么写过，被正则贪婪匹配坑了（`翻唱` 被 `唱` 抢先匹配，
"天童爱丽丝翻唱 群青YOASOBI" 因此判否）。
改成**直接看歌名后面那个字**，简单且不会因为多一个标记就失效。

实测效果（14 首歌真实搜索）：

    修前：4/11 命中，且命中的还有错的（群青→群青信号）
    修后：10/14 命中，**选中的都是对的那首**；未命中的确实是没有对应翻唱

### 20.4 问题四：说"停"停不下来

    用户："停"
    机器人：还是把歌发出来了

原因：结果**已经在返回路上**——只杀进程拦不住它。
修法两层：

1. `request_cancel()` 置标志 → 工作线程发现后 `taskkill /T` **真的杀掉子进程**；
   同时递增 **token** → 已跑完但还没发送的结果被判为**过期**，直接丢弃；
2. 新点一首会**顶替**旧任务（用户改主意了），旧结果同样作废。

端到端验证过：任务在跑 → 取消 → 结果变成"已按你的要求停下"，成品不发。

### 20.5 清理

缓存目录里留着 bug 时期的产物，歌名是畸形的：

    全速向光不是反乌托邦.mp3 / 错了罚你再唱一首准备出发.mp3
    蔚蓝档案的《准备出发.mp3 / 星塔旅人的《memoryofstella.mp3 …
    还有 55 秒规格做的 虫儿飞.mp3（当时还没改成 30 秒）

**全部删除**。只保留歌名正确、30 秒规格的两首：`世界执行我.mp3`、`反方向的钟.mp3`。

## 二十一、"一段时间没人理就断线"调查（2026-10-10）

用户反馈这个现象。**先说明：这块我之前没看过**，属于 NapCat↔QQ 那条链路，
不在我改过的代码里。以下是实际查到的，不是印象。

### 21.1 查到的现场（当时链路是**通的**）

    NoneBot PID 13288 在监听 8095，已运行 1.1 小时
    与 NapCat 有 1 条 Established 连接
    NapCat 反 WS 配置：AL-1S / 启用 / ws://127.0.0.1:8095/onebot/v11/ws
                      心跳 30000ms / 重连 30000ms / Token 空
    NapCat 的 QQ 进程在跑

也就是说：**我检查的那一刻，WS 层完全正常**。所以"断线"要么发生在别的时刻，
要么是另一种现象。

### 21.2 最可能的原因：QQ 登录被**静默**踢下线

NapCat 有个已知问题，标题就是这件事：

    NapNeko/NapCatQQ PR #2080
    "fix: 静默离线（无 KickedOffLine 通知）后自动恢复登录"

意思是：QQ 服务端把登录踢成离线，但**不发 KickedOffLine 通知**，
于是 NapCat 根本不知道自己离线了，也就不会去重连。
表现就是"没人理它一段时间后，发消息再也没反应"。

**为什么这个现象像"没人理就断线"**：空闲时机器人没有任何动作，
QQ 侧更容易把它判成不活跃；而它一旦静默离线，就没有任何机制能把它拉回来。

### 21.3 必须分清两种情况（对策相反）

从"机器人不回话"这个表象看，下面两种**完全一样**：

| | 现象 | 对策 |
|---|---|---|
| **A. 反向 WS 断了** | 8095 上没有 Established 连接 | NapCat 会按"重连间隔"（30 秒）自动重连；查配置或调小间隔 |
| **B. QQ 登录静默离线** | 8095 连接**正常**、进程也活着，但消息永远不来 | 重连 WS **没用**，只能重新登录 |

怎么区分：**在 QQ 里给机器人发一条消息，同时盯 run.py 控制台**。

    控制台有 "收到[...]" -> 链路正常，问题在别处
    控制台**一条日志都没有** -> 情况 B，登录被静默踢了

为此加了两个东西：

1. **适配层的连接日志**（`on_bot_connect` / `on_bot_disconnect`）——
   以前项目里**没有任何连接记录**，NoneBot 日志只在控制台、
   NapCat 的 logs 目录是空的，出了事无从查起。
2. **`scripts\链路体检.py`**——一条命令看全链路：
   进程是否在跑 / 端口是否有 Established 连接 / NapCat 进程 / 反 WS 配置。
   纯只读，不改任何配置。

### 21.4 顺带发现一个和"发不出媒体"有关的配置

    NapCat 配置里的 enableLocalFile2Url: False

这一项为 `false` 时，本地 `file://` 路径的媒体可能发不出去——
而我们发语音正是用 `[CQ:record,file=file:///D:/...]`。
**但你的截图里语音确实收到了**，所以目前是通的；
如果以后语音时好时坏，优先查这一项。

### 21.5 我没做的

* 没有改 NapCat 的任何配置（重连间隔、心跳都保持原样）；
* 没有上 NapCat 的修复版 PR #2080——那要动你的 NapCat 安装；
* **没有确认**你遇到的是 A 还是 B。这需要你复现时的一句话：

      发消息没反应时，run.py 控制台有没有打出 "收到[...]"？

  有 = A（或别的），没有 = B（登录静默离线）。

### 21.6 补充：断开是**哪一侧**断的，以及重连有多快

查了 NoneBot 源码，重连间隔是硬编码的：

    nonebot/adapters/onebot/v11/adapter.py:47
        RECONNECT_INTERVAL = 3.0

    失败时的日志："...Trying to reconnect..." 然后 asyncio.sleep(3)

所以恢复速度**不取决于 NoneBot**——它每 3 秒就试一次。
真正的瓶颈是 **NapCat 的「重连间隔」**：当前配置 **30000 ms（30 秒）**。
也就是最坏情况下，断开后要等半分钟 NapCat 才会发起新连接。
你看到控制台反复打 "Trying to reconnect..."，就是在等这个。

### 21.7 一个重要的发现：**适配层其实可以实跑**

交接文档第 8 节一直写着"适配层未实跑（PyPI 不可达）"。
这次查链路时发现：**项目自己的 venv 里已经装了 nonebot 2.5.0**
（`venv\Lib\site-packages\nonebot`）。

并且我按 `run.py` 的顺序实跑了一次加载：

    nonebot.init()
    driver.register_adapter(OneBotV11Adapter)
    nonebot.load_plugin("aliceqq.adapters.nonebot_plugin_alice")
    -> Succeeded to load plugin "nonebot_plugin_alice"

**结论：插件导入与注册是通的**（含我新加的连接钩子）。
之前"未实跑"的记录已过期，应改为"插件加载已验证；消息收发待实机确认"。

注意：直接 `import` 这个模块会报 `NoneBot has not been initialized`——
必须先 `nonebot.init()`，这是 NoneBot 的设计，不是 bug。

## 二十五、接通 tool calling，README 改为 Agent 定位（2026-10-10）

用户要求"**凸显 agent 的特点，向 GitHub 上 AI 结合项目的格式靠齐，
体现与 AI 的互动**"。做这件事的过程中**挖出一个大问题**。

### 25.1 挖出：整套 tool calling 是**死的**

准备写"Agent 架构"章节时，我想确认工具调用到底怎么触发的，
于是去读 `engine.generate_reply()`——发现：

    reply = self.llm.chat(messages, config=self.config.llm)
                                          ^^^^^^^^^^^^^^^^^ 没有 tools=

而 `OpenAICompatibleLLM.chat()` 的签名是：

    def chat(self, messages, *, config, tools=None):
        if tools:
            payload["tools"] = tools
            payload["tool_choice"] = "auto"
        ...
        tool_calls = message.get("tool_calls") or []      # 会解析

**没有传 `tools`，模型就不知道有工具可调，`reply.tool_calls` 恒为空**，
于是下面那段"执行工具 → 以 role=tool 回灌 → 二次生成"的循环
**永远不执行**。

工具此前只是以**文字**形式写在提示词里（`available_tools` 变量），
模型能看到工具名字，但**无法真正发起调用**——它只能在回复里
"声称"自己用了工具。

这是个典型的**接线漏洞**，而且特别难发现：

  * 注册表在、JSON Schema 在、执行器在、回灌循环在——**每一部分单独看都正确**；
  * 唯一的缺陷是调用时漏传了一个参数；
  * **没有任何报错**，测试全绿，模型回复看起来也正常。

修法很小：把 schema 传给 `llm.chat()`。顺带加了 `tools.openai_tool_schemas()`，
只把 **available=True** 的工具写进 schema（不可用的工具递给模型等于递刀子——
它会尝试调用、拿到失败、或者在回复里演一遍"我去查一下"）。

修完之后实测，模型**真的会调工具了**：

    ── 决策链 ──
      ① 模型决定调用  remember
      ② 执行结果      成功：已记录。
      ③ 二次生成      把工具结果作为 role=tool 回灌，再问一次模型
    [*] 工具: remember=ok

### 25.2 补了回归防线，并**验证过它真的能拦住**

新增 `tests/test_tool_calling.py`（9 项），其中两条专门盯接线：

    test_schema_is_passed_to_the_model      # 断言调用时 tools 非空
    test_second_call_also_carries_tools     # 二次生成也要带 tools

**光写测试不够，得证明它有效**。所以故意把 `tools=schemas or None`
改回 `tools=None` 跑了一遍，结果正好红两条，报的就是那句诊断：

    AssertionError: unexpectedly None :
      engine 必须把 tools 传给 llm.chat()——不传的话 tool_calls 永远是空的

确认有效后已恢复。**没验证过的测试等于装饰。**

### 25.3 写作过程中又发现：检索其实有**两条路径**

写 trace 时发现它报"未触发工具调用"，但检索明明发生了。

这是个挺实在的 agent 设计。所以 README 里把两条路径都画进了架构图，
`--trace` 也会区分显示：

    ① 模型调工具       -> role=tool 回灌
    ② 引擎判定先检索   -> 结果注入提示词

### 25.4 新增 `--trace`：把决策链打印出来

Agent 类项目有一半价值在"它怎么决定的"。新增 `python -m aliceqq --trace`，
输出模型、工具目录、工具调用与结果、检索来源与耗时、护栏拦截。

**只打印真实发生过的事**：没有工具调用就不打那一段，不存在的阶段绝不编造。

### 26.2 问题一：`.env.example` 里有**三段重复的 TTS 配置**

    TTS_VC_BLEND  行 237 给了 alice_ja:0.7,alice_zh:0.3

一共 8 个键重复。危害和前几节记过的那次**完全一样**：
后面的值静默覆盖前面的，配置改了不生效、而且没有任何提示。

**为什么它能藏这么久**：项目自检只检查了 `.env`，
而 `.env` 不入库、每个人不同——**模板本身从来没被检查过**。
所以模板里的缺陷一直没人发现，直到有人在干净目录 clone 下来生成配置。

两处修复：

1. 合并三段为一段，并去掉那个空值覆盖；
2. **自检把 `.env.example` 也纳入检查**（`【4】.env 结构` 现在是两项：
   模板 + 真实 .env）。这条是根本性的——它保证以后不会再复发。

### 26.3 问题二：`_run()` 没给子进程设 UTF-8，撞上 cp936

用户看到的报错：

    自动安装失败：decoding with 'cp936' codec failed

看起来像网络或包的问题，**完全指不到真因**。实际原因：
`bootstrap._run()` 用了 `capture_output=True` 但**没传 `env`**，
于是子进程（pip、自检脚本）继承默认的 cp936(GBK) 环境，
往管道里写非 GBK 能表示的内容时就报这个错。

修法：显式给子进程设 `PYTHONUTF8=1` 与 `PYTHONIOENCODING=utf-8`。
顺便把 `cwd=ROOT` 也固定下来——自检脚本靠相对路径找 `.gitignore`
和 `tests/`，工作目录不对会得出错误结论。

### 26.4 问题三：失败时显示空白，等于没提示

用户的输出里出现：

    项目自检：✗          <- 后面什么都没有

**这比直接报错还糟**——完全不知道该做什么。
根因是自检结果的解析逻辑太脆：拿不到"通过 X｜需注意 Y"这行时，
`detail` 就是空串。

修法：解析不出内容时**把原始输出的末尾带出来**，
哪怕乱码也比空白强（至少能看出是脚本崩了、还是符号没匹配上）。

### 26.5 问题四：`--repl` 的 `:prompt` 容易误解

用户实际操作序列暴露了这个：

    你 > :prompt
    （这次要发给爱丽丝的内容）你 > prompt     <- 顺手把 "prompt" 发出去了

原设计的 `:prompt` 是"**为下一条消息**显示提示词"，
所以它会再问一次内容。但用户敲 `:prompt` 之后又看到提示符，
自然就接着输入了——结果那句字符串被当成真实消息处理。

改成更符合直觉的两种用法：

    :prompt            重看**上一条**消息的提示词（默认，最常用）
    :prompt <内容>     先发这条，再打印它的提示词

### 26.6 教训：本机"什么都装了"会掩盖问题

这次四个问题里，**有三个在本机完全测不出来**：

| 问题 | 为什么本机测不出 |
|---|---|
| 模板重复键 | 本机 `.env` 是早期手工改过、已经干净的 |
| cp936 编码 | 本机一直带着 `PYTHONUTF8=1` 跑，覆盖了默认行为 |
| 空白的失败提示 | 本机自检一直是绿的，走不到失败分支 |

**干净目录验证是唯一能发现这类问题的方法。** 建议列为每次交付前的固定动作。

### 28.1 推送过程踩的三个坑（都值得记）

**坑一：`git push` 报 "Connection was reset"，但真因是死代理**

用户看到的报错：

    浏览器  Failed to load resource: net::ERR_CONNECTION_RESET
    git     Recv failure: Connection was reset

**看起来像 GitHub 被墙、或认证失败、或仓库不存在——全都不是。**
真因是：代理客户端（FlClash/xray）挂了，**但 Windows 系统代理
仍然指向那个已经不监听的端口**。于是所有走系统代理的程序
把流量发到一个死端口。

排查方法很直接，但当时完全没想到：

    Get-NetTCPConnection -LocalPort 11808 -State Listen   # 空 = 没有程序在监听
    Get-Process xray                                      # 进程已不在

而且这个状态下**多个程序会同时失效**（浏览器 + git），
这个"同时"本身就是线索——如果只是 GitHub 被墙，
不至于连认证弹窗都打不开。

教训：**报错指向哪里，不等于问题在哪里。** 先确认本机代理状态。

**坑二：我给 git 配的代理后来反而成了负担**

排查过程中我给仓库配了 `http.proxy`（那时代理是活的、直连不通）。
后来代理挂掉，这个配置就让 git 一直去撞死端口。
而当时**直连其实是通的**（实测 github.com 直连 200）。

教训：网络环境会变，代理配置要跟着变。`scripts\推送GitHub.py`
因此把"系统代理是否可用"放在第 0 步先探测。

**坑三：GitHub 的"push 自动创建仓库"不可靠**

我一直以为 `git push` 到不存在的仓库时会自动创建。实测：

    认证成功 -> remote: Repository not found.

**没有自动创建。** 这个便利功能取决于凭据类型与账号设置，不能依赖。
正确做法是**先在网页上建空仓库**（不勾 README/.gitignore/license），再 push。

## 二十九、多模态第一步：图片理解（2026-10-11）

用户提出把项目做成"**面向真实消息平台的可控多模态 Agent**"。
这一节记录第一阶段的落地：让模型真的能看懂用户发来的图。

### 29.1 先做了审计，发现"多模态"名不副实

三个实证：

    1) aliceqq/ 里搜不到任何 vision / image_url / 多模态 代码
    2) llm.py:  Message = Dict[str, str]      <- 装不下多模态 content 数组
    3) IncomingMessage 只有 text 字段，没有 images

更具体地说，适配层只调了 `event.get_plaintext()`，
**图片段既不进文本也不进别的字段，直接被丢掉**。
所以在此之前，"理解图片"这件事在架构上就是不可能的。

而 README 里写着"多模态"——它其实只能**发**图（表情包回声、
素材库、AI 生成），不能**看**图。这个词当时是不准确的。

### 29.2 三个阶段的关键词现状（审计结论）

| 关键词 | 现状 |
|---|---|
| **可控** | 已经相当扎实：`policy.py` 有访问控制、限流、按能力独立额度、审核审计日志 |
| **多模态** | 几乎为零（上面三个实证） |
| **真实消息平台** | 适配层只有"能加载"的测试，没有集成测试 |

所以最大的缺口是图片理解，而且它是**架构级**的（消息类型要改）。

### 29.3 设计取舍

**① 走云端 OpenAI 兼容接口，不做本地推理。**
核心包必须零第三方依赖（899 项测试靠这一点才能离线跑），
所以不能为了看图去 import transformers/torch。
视觉模型通过 HTTP 端点接入，端点可配，换厂商只改三个环境变量。

**② 它是"感知"步骤，不是"工具"。**
工具是模型自己决定要不要调的（比如要不要联网查）。
但"用户发了图"是**事实**——模型没法"决定不看"，它得先知道图里有什么才有得选。
所以视觉结果直接注入对话上下文，而不是挂成 `describe_image` 等模型来调。

**③ 没配就如实说。** 没有视觉模型时注入一段"你这次没有看到图片内容"，
并明确要求模型告诉用户、**不要猜图里是什么**。
不注入的话，模型会以为没图这回事，转而根据用户的话编一个画面。

**④ 按张独立计额度。** 和"生成图片"是两件事，额度分开
（`daily_vision = 100`）。一次最多看 3 张：群聊里连发多图很常见，
不设上限成本和延迟都会翻倍。

**① `build_client` 用错了字段名，而且没有任何报错。**

**② 测试里的 `_patch_net` 用 lambda 再包了一层。**

m.open = lambda request, timeout: fake_open(request, timeout)

这样第一个位置参数会被当成 `fake_open` 传进去，`m.open` 成了签名对不上的

## 三十、多模态第二步：语音理解（2026-10-11）

按"面向真实消息平台的可控多模态 Agent"这个目标继续。

### 30.1 断得比图片还彻底

    asr.py 早就有转写能力，也早就配好了（ASR_PROVIDER=local，本地 whisper）
    但它只被用在"转写 B 站视频音轨"那一条链路上
    用户直接发来的语音消息 —— 适配层根本没抽 record 段

所以模型收到的是一条空文本。表现是"发语音它不回"。
**能力、配置、依赖全都在，只是没接线。**

### 30.2 顺带挖出一个更大的问题：纯媒体消息被当空消息丢掉

修的过程中发现 `handle()` 开头有这么一段：

```python
# 0) 太短/空消息
if not text:
    outcome.reason = "空消息"
    return outcome
```

它**只看 text**。而用户直接甩一张图、或者发条语音不说话，
text 都是空的——于是这类消息在真实 QQ 上被直接 return，
后面的图片理解和语音识别**一次都不会执行**。

实测证据：

    手工调 _analyze_audio -> {'ok': True, 'chars': 11, 'elapsed': 4.33}
    handle 的 debug keys   -> []
    handle 的 decision     -> silent, reason='空消息'

**两个多模态功能都做了，但都会被这一行挡在门外。**
如果只做单元测试、不上真实场景，这个问题不会暴露——
它需要"一条没有文字的消息"这个组合才会触发。

修法：`if not text and not message.has_media_input`。

## 三十一、多轮工具编排（ReAct 循环）（2026-10-11）

目标里明确列的一项。原来的实现只做一个来回：

    模型要工具 -> 执行 -> 以 role=tool 回灌 -> 再问一次 -> 结束

而且那次"再问一次"外面套着 `except LLMError: pass`——**失败了什么也不说**。

### 31.1 改成真正的循环

    模型要工具 -> 执行 -> 回灌 -> 再问
              -> 它可能还要下一个工具 -> 继续
              -> 直到它给出文字，或撞上轮数上限

实测（`remember` 接 `academic_search`）：

    模型调用次数   3
    工具循环轮数   2
    用到的工具     ['remember', 'academic_search']
    角色序列       第1次 [system, user]
                  第2次 [system, user, assistant, tool]
                  第3次 [system, user, assistant, tool]

`role=tool` 一轮一轮累积下去，模型看得到前面所有工具的结果。

### 31.2 三条约束，都是有意加的

**① 有轮数上限（默认 3，可配，夹在 1..6）。**
模型可能一直调工具不出结论。撞上限时**如实说明**
（"查了几轮还没理清楚"），不假装答完了——
和项目其它护栏同一个取舍：宁可说没查清，也不编结论。

配置项是 `LLM_MAX_TOOL_ROUNDS`。上限被夹住，
避免配置写成无限循环。

**② 同一个工具不重复调。**
带不同参数不算重复（先查 A 的论文再查 B 的，是正当用法）；
但**完全相同的调用**再来一次只会浪费额度和时间，
而且往往意味着模型在绕圈。这种调用不再执行，
但仍然回灌一条"这个刚刚已经执行过了"，
否则模型会以为是失败而重试。

**③ 失败不再静默。**
某轮调用模型失败时，把原因记进 `debug["tool_loop_error"]`，
并用已有的结果组织一句回复，而不是无声无息。

### 31.3 顺带挖出一个更实际的问题：记忆被写了两遍

写"重复调用"的测试时，断言"同一个 remember 只该写一条记忆"
得到了 2。查下去发现**不是去重失效**，而是两条独立路径都写了：

    source='explicit'   "用户明确要求记住：我喜欢猫"   <- 启发式，在调用模型前就写了
    source='tool'       "猫"                        <- remember 工具写的

`_remember_from_message` 是**确定性**的记忆提取，
跑在调用模型**之前**（顺序不能反：模型需要看到已保存的记忆），
所以它没法提前知道模型会不会调工具。两条都成立时就重复了。

这很实际：用户说一句"记住 X"，记忆库里就多一条语义重复的记录，
`/记忆` 会把两条都列出来。

**修法**：`_remember_from_message` 增加一个前置判断——
本轮如果已经通过 `remember` 工具成功写入过，启发式就让路。
为此把它的调用点从"模型调用之前"挪到"之后"（错误分支和
检索澄清分支也都补上了调用）。

让工具优先的理由：工具写的是模型**明确表达**要保存的内容
（"猫"），比启发式从原话里切出来的（"用户明确要求记住：我喜欢猫"）
更准。

验证：

    调 remember 工具 -> 记忆 1 条，source='tool'
    不调工具         -> 记忆 1 条，source='explicit'

**两条路径都还能工作，只是不再同时写入。**

### 31.4 为什么既有测试没抓到这个重复

现有断言用的是 `assertGreaterEqual(count, 1)` 这种写法，
所以"多写了一条"不会失败。新测试改成了精确断言，
并且额外断言 `source`——这样"去重坏了"和"启发式没让路"
两种不同的故障能区分开（只坏一条是 2 条，两条都坏是 3 条）。

## 三十二、多模态第三步：视频输入（2026-10-11）

目标里"多模态=真实能理解图片/语音/视频"的第三块。做完这一块，
三种输入都通了。

### 32.1 设计：复用已有两条链路，不另起一套

    视频 --抽帧--> JPEG --+--> VisionClient（图片理解那条）
         --抽音轨--> WAV --+--> ASR（语音理解那条）

这样做的好处很实际：**视频不需要新的模型、新的额度类型、新的护栏**。
`vision` 和 `asr_voice` 的门禁与额度自动生效，
"看不到就说看不到"的护栏也自动继承。有一条测试专门守着这一点：

    quota_vision_user    = 1   <- 抽帧走图片额度
    quota_asrvoice_user  = 1   <- 音轨走语音额度
    quota_video_user     = 0   <- 不该凭空多出一个 video 类型

### 32.2 三个实测踩到的技术点

**① 视频不能用管道喂给 ffmpeg。**
`ffmpeg.extract_segment` 一直是走 `pipe:0` 的（音频可以），
但 mp4 的 `moov` box 可能在文件尾部，需要可 seek 才能解析。
所以视频一律先落临时文件——这和 `probe_duration` 里
早先记过的原因是同一类。

**② MP4 也**不能**输出到管道。**
造测试视频时撞上的：muxer 需要可 seek 的输出。
所以造测试数据要先写文件再读回来。

**③ 抽帧要缩到 640 宽。**
视觉接口按图算钱，1080p 一帧可能好几 MB，base64 后还要涨 1/3。
缩到 640 宽后每帧通常几十 KB（实测 2521 字节），
对"看懂发生了什么"完全够用。

抽 3 帧而不是 1 帧：短视频画面变化快，一张往往看不出在做什么；
3 帧的成本增加有限。实测 3 帧耗时 0.2 秒。

### 32.3 边界情况都当成一等情况处理

| 情况 | 处理 |
|---|---|
| 没有音轨 | **不是错误**。纯画面视频很常见，抽帧照样能用 |
| 抽不出帧但有声音 | 仍然算成功——"有人说话"值得听 |
| 两部分都失败 | 才报失败，且要说明原因 |
| 视频很长 | 音轨只转写前 120 秒（又慢又贵，开场通常已含主要信息） |
| 有 duration 字段 | 直接用，省一次完整解码探测 |

### 32.4 实测结果

用 ffmpeg 合成了一段 3 秒测试视频（深蓝底 + 白字 `ALICE VIDEO 5570`
+ 音轨"这是爱丽丝的测试视频"）：

    debug.video = {'ok': True, 'frames': 3, 'frames_ok': True,
                   'has_audio': True, 'transcript_chars': 10,
                   'elapsed': 11.53}

    注入提示词：
      【画面】图片为纯深蓝色背景，左下角有一行白色文字："ALICE VIDEO 5570"
      【声音】视频音轨转写：這是愛麗絲的測試視頻

    模型回复：
      "爱丽丝看到了！从机器抽出来的几帧画面看——
       **画面部分**：纯深蓝色背景，左下角有一行白色文字「ALICE VIDEO 5570」…
       **声音部分**：音轨转写出来是「這是愛麗絲的測試視頻」。"

模型**主动区分了两个来源**（"从抽出来的几帧画面看"），
这正是提示词里要求的行为——它没有假装自己看过整段视频。

### 32.5 顺带确认了一件事：AMR 能直接识别

QQ 语音常用 AMR 格式。实测先转成 AMR（4742 字节）再喂给

所以不需要额外转码。

## 三十三、适配层集成测试：真的把 `_handle` 跑起来（2026-10-11）

目标里"真实消息平台=适配层经过实机验证而非只有加载测试"。
上一轮补了 28 项离线测试，但那些测的是 `media_input` 里的纯函数
**和静态接线检查**——它证明不了"事件真的走到了引擎"。

原因还是那个：适配层整个包在 `if HAS_NONEBOT:` 里，
零依赖的 CI 里那段代码根本不存在。

### 33.1 解法：一个最小 NoneBot 桩

新增 `tests/_nonebot_stub.py`，提供适配层真正用到的那几个名字：

    get_driver / on_message / on_notice / PluginMetadata
    Bot / Message / MessageEvent / PrivateMessageEvent
    GroupIncreaseNoticeEvent / GroupDecreaseNoticeEvent

装好之后 `_handle` 会被注册进 `HANDLERS`，测试可以直接调用它。
于是"事件 -> 抽取 -> IncomingMessage -> 引擎 -> 回复"整条路径
从"静态检查"升级成**真的执行过**。

新增 `tests/test_adapter_integration.py`（17 项）覆盖：

| 用例 | 验证什么 |
|---|---|
| 图片段到达引擎 | `IncomingMessage.has_images` 为真 |
| 纯图片消息到达引擎 | 不说话也不能被当空消息丢掉 |
| 语音段到达引擎 | `has_audios` 为真，duration 解析正确 |
| 视频段到达引擎 | `has_videos` 为真 |
| 三种模态同一条消息 | 三个字段都为真，文字不受影响 |
| 私聊/群聊元信息 | is_private / group_id / message_id / timestamp |
| 机器人自己的消息 | 不进引擎（否则自问自答） |
| 纯文本路径 | 加了媒体抽取没把普通路径弄坏 |
| 未知段类型 | 被忽略，不影响文字 |
| 空消息 / 坏段 | 不抛异常 |
| 端到端带图片 | 真的触发视觉并发出回复 |

### 33.2 这个桩能证明什么、不能证明什么

**能证明**：适配层自身的接线是对的——事件里的媒体字段被正确取到、
放进了 `IncomingMessage`、走到了引擎、引擎发出了回复。

**不能证明**：NoneBot 真的会派发事件；QQ/NapCat 给的字段名和
文档一致；真实网络下媒体的下载与解码。这些只能靠真机。

所以它是**真机验证的补充而不是替代**。价值在于：它把
"适配层自己写错了"这一类问题拦在了提交之前，
而这类问题在真机上极难定位——图片那次就是这样：
抽取函数写对了，但没人验证它是否真的被调用。

### 33.3 意外收获：实证了工具 schema 真的传给了模型

第一次跑集成测试时忘了替换 LLM，于是走了真实 API。
日志里出现了这一行：

    'tools_offered': ['remember', 'web_search', 'academic_search']

**这是工具接线在真实 API 调用下确实生效的直接证据。**
第 25 节记过那个 bug——`llm.chat()` 支持 `tools=` 也会解析
`tool_calls`，但引擎从未传参，于是整套 function calling 静默失效。
现在有一条真实链路的日志证明它是通的。

### 33.4 测试性能：从 89 秒压回 10 秒

第一版这 17 个用例跑了 **89 秒**。查下来是两类真实网络等待：

**① 假域名被真的去下载。** 事件里的 `https://cdn/v.amr` 是假域名，
而 `read_media_bytes` 会走完整的 DNS 解析 + 20 秒超时 + 2 次重试
（单独实测一次 15.5 秒）。17 个用例几乎全花在等这个。

修法：把 `media.read_media_bytes` 也挡掉，按扩展名返回
**带正确魔数的假字节**——后面的 MIME 判断、解码仍然走真实分支，
只是不碰网络。89 秒 -> 10 秒。

**② 视觉接口被真的请求。** 同一个原因，修补后仍有 8~17 秒的等待。

**教训**：单元/集成测试必须离线、确定、快——这三条是同一个要求。
**"能过但很慢"是一种需要修的失败**，因为它会让人不想跑测试。

### 33.5 顺带修掉一个输出噪音

用户 `.env` 里有 `ALICE_DEBUG=1`，模块导入阶段就把调试开关打开了，
于是每个用例都往 test runner 的输出里灌一大段事件原文和引擎决策，
把真正的测试结果淹掉（`Ran 899 tests` 那行都被埋了）。
现在 `setUpClass` 里临时把 `_log` / `_debug_log` 换成空实现，测完还原。

## 三十四、对照 OneBot 规范核查，发现 `base64://` 完全没处理（2026-10-11）

集成测试做完之后，我去**核对字段名**——因为"适配层接线对不对"
最终取决于"QQ 到底发什么字段"，而这只能查规范，不能凭记忆。

### 34.1 核查结果：字段名猜对了，但漏了一种来源形式

拉取 OneBot v11 规范（`botuniverse/onebot-11` 的
`message/segment.md`），图片/语音/短视频三段都只收两个字段：

| 段类型 | 字段 | 收 |
|---|---|---|
| image | `file` | ✓ |
| image | `url` | ✓ |
| image | `type` | ✓（`flash` 表示闪照） |
| record | `file` / `url` / `magic` | ✓ |
| video | `file` / `url` | ✓ |

**`duration` 不在规范里**——它是 NapCat 的扩展。
我的代码用它只是省一次解码探测，没有也能退回 `probe_duration`，
所以这里没问题（顺带在注释里写明了这一点）。

`file` 和 `url` 我都在用，`face` / `flash` 也处理了。
但规范里还有一句我漏掉了：

> 发送时，`file` 参数除了支持使用收到的图片文件名直接发送外，还支持：
> 绝对路径（`file:///...`）、网络 URL、**Base64 编码（`base64://...`）**

而 NapCat 的配置里 `enableLocalFile2Url=false` 时，
它更可能直接给 base64 而不是可访问的网址。

### 34.2 实测确认这是个静默失效

    read_media_bytes("base64://...")  ->  b""（0 字节）
    ImageRef.to_data_uri()            ->  ""（空串）

**没有任何报错**，只有"它看不见我发的东西"。而且三种模态一起失效。

### 34.3 修的过程里出现了"只修好两种"

第一次修只改了 `read_media_bytes`，于是：

    语音  ✅ 读到了 24 字节   （走 read_media_bytes）
    视频  ✅ 读到了 12 字节   （走 read_media_bytes）
    图片  ❌ to_data_uri 仍然是 0  （走 ImageRef.to_data_uri，只认本地 path）

**图片走的是另一条路**。原因是规范里 base64 来自 `file` 字段，
而适配层把 `file` 放进 `path`、`url` 才放进 `url`，
我的 `to_data_uri` 只检查了 `url`。

这种"三种模态里坏一种"的偏差是最容易漏的——如果只测一种
（比如只测图片），反而看不到语音/视频已经好了；
如果只测语音，就永远发现不了图片还坏着。

所以新增的 `tests/test_media_base64.py`（19 项）是**逐模态**覆盖的，
另外有一条 `AllModalitiesTest` 一次性验三种，专门防这种偏差。

### 34.4 顺带补上的两处

`ImageRef.to_data_uri` 现在还支持：
  * `url` 字段直接给 http(s) 时自己下载（以前只有本地 path 和 blob 两条路）；
  * 两个字段都检查 base64。

### 34.5 这次核查的教训

**"我的代码假设了什么"要写下来再去核对。**
我做的方式是先列出代码里所有 `data.get(...)` 的字段名，
再去规范里逐个对——这样能发现"假设错了"和"漏了分支"两类问题。
凭记忆写适配层是这次唯一真正的风险来源，因为真实 QQ 的行为
我无法在本地复现。
