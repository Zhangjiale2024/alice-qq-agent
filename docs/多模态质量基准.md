# 多模态理解质量基准

这份文档记录**实测数字**，不是感觉。

写它的原因：ASR 那边我先观察到一个错误（"爱丽丝 → 艾利斯"）就想去修同音字，
做了基准之后发现**方向完全是错的**（真因是繁体字，占比 11/12 而不是 1/12）。
那一次说明"先量再改"能省掉大量白做的事。

所以这里把多模态各条链路的基准固定下来，避免以后凭印象改动。

---

## 一、语音识别（ASR）

### 方法

TTS 合成 12 条已知句子（角色专名、游戏术语、日常句、时间、术语），
用本地 `faster-whisper` 的 `small` 模型转写，按**字符级编辑距离**算错误率
（去掉标点和空白后比对，不需要分词，也就不用引第三方库）。

### 基线

```
样本 12 条 | 完全正确 0 条 (0%) | 平均字符错误率 40.6%
```

### 主导错误是繁体字，不是同音字

```
今天天气看起来还不错    -> 今天天氣看起來還不錯
量子纠缠是物理学中的概念 -> 量子糾纏是物理学中的概念
明天下午三点开会       -> 明天下午3點開會
这个关卡爱丽丝打不过去  -> 這個關卡,愛麗絲打不過去
```

真正的同音字错误只有 1/12（爱丽丝 → 艾利斯）。

**这一条直接否掉了"做同音字词典"的方案**——那个方案最多修 1 条。

### 七种方案对比（同一批语音）

| 方案 | 平均错误率 | 完全正确 |
|---|---|---|
| A 基线 | 40.6% | 0/12 |
| B `initial_prompt` 只要简体 | 14.2% | 5/12 |
| **C 提示简体 + 角色专名** | **1.0%** | **11/12** |
| D `temperature=0` | 40.6% | 0/12 |
| E B+D | 1.0% | 11/12 |
| F 事后做简繁转换 | 7.0% | 8/12 |
| G C+F | 1.0% | 11/12 |

采用 **C**。耗时几乎不变（2.6s → 2.5s），不加依赖，不改模型。

### 三个被数据否掉的方案

| 想法 | 实测 | 为什么不行 |
|---|---|---|
| 做同音字词典 | 最多修 1/12 | 提示词能修 11/12 |
| 事后做简繁转换 | 7.0% | 不如直接提示的 1.0%，还多一层机制 |
| 代码把阿拉伯数字转汉字 | **制造新错误** | "10点" 被逐字替换成 "一零点"；提示词里说一句就够 |

剩下唯一一条残留是 `明天下午三点开会` → `明天下午3点开会`，
提示词里加"数字也用汉字写"之后也为 0 了。

### 端到端确认

用 `build_client` 造出**引擎在用的那个客户端**跑（真实路径）：

```
旧：不加提示         错误率 40.6%  完全正确  0/12
新：简体+数字        错误率 15.9%  完全正确  5/12
新：再加角色专名表    错误率  1.0%  完全正确 11/12
```

## 二、图片理解（Vision）

### 方法

用 PIL 自己造图，**内容完全可控**，拿真实视觉接口（`qwen3-vl-plus`）跑，
逐项打分。两个指标：

* **关键事实命中率** —— 预设的文字/颜色/数量有没有读出来
* **编造次数** —— 描述里出现图里**没有**的东西

第二个更重要：漏读用户能看出来，编造看不出来。

### 结果

```
用例 8 | 完全正确 8/8 (100%)
关键事实命中 14/14 (100%)
编造次数 0
```

用例覆盖：精确编号、字母+数字、数红圆（3 个）、数蓝圆（5 个）、
三色块顺序、全白空图、纯灰图、登录界面（含 3 处文字）。

**空图和纯色图没有硬凑内容**——模型的回答是
"图中是一片纯白色，没有任何可见的物体、文字或图案"。
这一条很重要，因为模型有编造出内容的动机（用户显然期待看到东西）。

### 这个基准的局限（必须写明）

**我的图都是"干净"的**：纯色背景 + 大号黑字 + 简单几何。
真实 QQ 图片是截图、表情包、照片，有噪点、旋转、小字、复杂背景。
所以 100% 只能说明"干净图上的理解是可靠的"，
**不能推出"真实图片上也这样"**。

要测真实图片需要真实素材，而那需要人提供 —— 这也是真机验证还没做的同一个原因。

### 字符级精确度：不需要改，提示词已经够了

观察到一次 `ALICE-7391` 被读成 `ALICE:7391`（连字符变冒号），
怀疑提示词没说清标点。于是对比三种提示词：

```
现状提示词         6/7
强调符号          6/7
强调符号+格式      6/7
```

**三种完全相同。** 而且逐条看，现状提示词在这些场景**全对**：

```
ALICE-7391        -> "ALICE-7391"
user_name_42      -> "user_name_42"
a@b.com           -> "a@b.com"
203.0.113.7       -> "203.0.113.7"
https://x.io/a    -> "https://x.io/a"
A1-B2_C3.4        -> "A1-B2_C3.4"
```

那次 `ALICE:7391` 是**偶发**，不是系统性问题。

第 7 个用例（`订单号：XY-2024-77`）失败的原因是**我自己的测试图**：
PIL 的默认位图字体画不出中文，"订单号"三个字渲染成了方块。
模型看到方块就说"前三个字符为方块符号，无法识别"——**它是对的**。
换成真实中文字体之后读对了。

**结论：视觉提示词不改。** 没有证据支持改动，
而"强调符号+格式"那种更复杂的提示词并没有更好——
加了只是让代码更长。这和 ASR 那边被否掉的三个方案是同一个教训。

## 三、视频

视频没有单独的质量基准，因为它**复用上面两条链路**：
抽帧交给视觉、音轨交给 ASR。所以上面两个数字基本能代表它的质量。

已验证的是**工程正确性**（见 `tests/test_video_input.py` 39 项）：

* 没有音轨不是错误（纯画面视频常见）
* 抽不出帧但有声音仍算成功
* 长视频只转写前 120 秒
* 抽帧缩到 640 宽（视觉按图计费）
* 视频不新增额度类型，走 `vision` + `asr_voice`

实测一条 3 秒视频：3 帧 + 音轨转写，11.5 秒完成，
模型主动区分"从抽帧看"和"从音轨听"，没有假装看过全片。

## 四、这份文档想说明的方法论

**先量再改。** 两个方向上我都基于单个观察形成了判断，而基准数据两次都否掉了它：

* ASR：以为主要问题是同音字 → 实际是繁体字（11/12 vs 1/12）
* Vision：以为提示词没强调标点 → 三种提示词完全一样，现状已经够好

**"看起来在做事"和"真的有用"是两件事。** 被否掉的五个方案
（同音字词典、事后简繁转换、代码转数字、ASCII 过滤、更复杂的视觉提示词）
共同点是：都能写出一堆代码、都能让提交看起来更丰富，
但实测都不如一个更简单的办法。

**如果不做基准，这五个我都会做进去，然后"感觉好了一点"。**
