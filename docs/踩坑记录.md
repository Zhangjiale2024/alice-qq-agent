# 踩坑记录

这份文档记录的是这个项目里**真实发生过**的故障，以及我是怎么找到原因的。

放在这里是因为这些东西比功能列表更有价值。而且里面有几个是我一开始
判断错了、绕了很远才回到正路上的——那些过程也一并写下来了，
因为下次遇到同类问题，能想起"报错指向的地方不一定是问题所在"就够了。

## 一、工具调用从来没触发过

### 现象

功能看起来都正常。模型会回复，会说"我记住了""我去查一下"。
但我去看日志，`tool_results` 一直是空的。

### 排查

我先把 `tools.py` 从头读了一遍。注册表在，两个工具的 JSON Schema 写得很完整，
`available` 标记也对。然后看 `engine.py` 里处理工具调用的那段：

```python
if reply.tool_calls:
    followup_messages = list(messages)
    ...
    for call in reply.tool_calls:
        result = self._execute_tool(name, arguments, message, outcome)
```

执行器、`role=tool` 回灌、二次生成——全都在，写得很完整。

再看 `llm.py` 里怎么解析响应：

```python
tool_calls = message.get("tool_calls") or []
```

也在。

那就只剩一个问题了：`reply.tool_calls` 为什么会是空的。回到 `generate_reply`：

```python
reply = self.llm.chat(messages, config=self.config.llm)
```

签名是：

```python
def chat(self, messages, *, config, tools=None) -> Reply:
    ...
    if tools:
        payload["tools"] = tools
        payload["tool_choice"] = "auto"
```

**没传 `tools`。**

### 原因

不传 `tools`，模型就不知道有工具可以用，自然不会返回 `tool_calls`。
下面那段精心写好的执行和回灌逻辑，**一次也不会执行**。

工具此前只是以文字形式出现在提示词里（`available_tools` 这个变量），
模型能看到工具的名字和说明，但没法真正发起调用。
所以它只能在回复里"表演"自己用了工具。

### 为什么难发现

- 注册表、schema、执行器、回灌循环，每个部分单独看都对
- 唯一的缺陷是调用时漏了一个参数
- **没有任何报错**，测试全绿，模型回复看起来也正常
- 提示词里确实写了工具目录，所以"看起来很完整"

### 修复

在 `engine.py` 里把 schema 传进去：

```python
schemas = tools_mod.openai_tool_schemas(
    self.config, bool(self.search_service), bool(self.academic_service))
reply = self.llm.chat(messages, config=self.config.llm, tools=schemas or None)
```

同时给 `tools.py` 加了 `openai_tool_schemas()`，**只把 `available=True`
的工具写进 schema**。不可用的工具绝不能递给模型——它会去调、拿到失败、
或者在回复里演一遍"我去查一下"。

二次生成也带上 `tools`，否则模型没法连续调第二个工具。

### 加了回归测试，并验证过它真的有效

`tests/test_tool_calling.py` 里两条专门盯接线：

```
test_schema_is_passed_to_the_model      # 断言调用时 tools 非空
test_second_call_also_carries_tools     # 二次生成也要带 tools
```

光写测试不够，得证明它有用。所以我把 `tools=schemas or None`
改回 `tools=None` 跑了一遍，正好红两条，报的就是那句诊断：

```
AssertionError: unexpectedly None :
  engine 必须把 tools 传给 llm.chat()——不传的话 tool_calls 永远是空的
```

确认有效之后才恢复。

## 二、语音发不出去

### 现象

用户说"你来唱给我听，把语音发给我"，机器人回了一堆字，
但没有语音附件。

### 排查

先看意图识别。原来的正则只匹配"发...语音"这个顺序，
而用户说的是"把语音发给我"——语序是反的。补上之后以为好了。

结果还是不行。这次去看语音生成那条链路，发现返回的 provider 是
`baidu(备用)`，不是 `gptsovits`。

也就是说克隆音色的服务调用失败了，被 `FallbackTTS` 静默降级了。
去服务端看，返回的是 HTTP 400，报：

```
Resource 'cmudict' not found
```

### 原因

用户的测试文本里夹了英文（"唱 Na~ LiLaBaLiLa~ 那段"）。
GPT-SoVITS 处理英文要过 `g2p_en`，而它依赖 nltk 的资源包，
那个环境里没装。

**两个问题都有，我只是先修了显眼的那个。**

### 修复

装了两个 nltk 资源（`cmudict` 从本地的 `GPT_SoVITS/text/cmudict.rep` 装，
词性标注器从镜像下），然后**重启服务**——`g2p_en` 是 import 时加载的，
不重启不生效。

### 留下的教训

静默降级很危险。`FallbackTTS` 的存在是对的（服务挂了还能出声），
但它不该让失败无声无息。现在 `--check-voice` 会把 provider 打出来，
听感不对时能立刻知道是不是回退了。

## 三、长音频转换崩 0xC0000005

### 现象

RVC 转换短音频正常，长一点的就开始崩。退出码 `-1073741819`。

这个数字是 `0xC0000005`，Windows 的访问违规。但**没有 Python 异常**，
没有 traceback，进程就没了。

### 我一开始的判断（错的）

看到"有时成功有时失败"，我当成间歇性故障，去怀疑：
是不是 torch 的线程问题、是不是 faiss 不稳、是不是音频格式不对。

试了限制 `OMP_NUM_THREADS=1`，没用。
对比成功和失败的输入格式——都是 44100Hz 立体声 PCM_16，没区别。

### 真正的原因

后来有一次报错变得具体了：

```
ImportError: DLL load failed while importing parselmouth: 页面文件太小，无法完成操作。
```

**"页面文件太小"** ——是 Windows 虚拟内存不够。

查配置：

```
提交上限      53.3 GB
可用虚拟内存   1.7 GB        <- 几乎耗尽
页面文件      C:\pagefile.sys 已分配 38.4 GB，但 C 盘只剩 11.3 GB
```

占用提交内存的是：数据库服务 10.7 GB，两个游戏加起来 10.6 GB。

**关掉游戏之后，可用虚拟内存回到 13.6 GB，同样的转换立刻正常。**

### 留下的教训

**报错指向哪里，不等于问题在哪里。** 我在这上面绕了很久，
因为崩溃发生在转换过程中，就一直在转换逻辑里找。

后来能定位是因为报错信息终于变具体了。
教训是：遇到原生层崩溃时，先看**退出码**，再看机器的资源状况，
而不是立刻怀疑自己的代码。

另外这也解释了一件事：为什么"短音频好、长音频崩"——
不是长度本身，是长音频需要更多内存，而当时余量已经不够了。

## 四、跨采样率比较得出的假结论

### 现象

转换后的音频"听着有点哑"。我做了个诊断，量了几个指标，
其中一项是 4–10kHz 的能量占比，想着它高就说明有高频噪声。

结果：

```
源    4-10k = 0.4265
成品  4-10k = 0.6433
```

看起来转换让高频涨了 50%，于是我从这个方向去调参数。

### 问题

我的诊断脚本用 22050 Hz 读取音频。而**源是 44100 Hz，成品是 40000 Hz**。
重采样到同一采样率之后，两者的奈奎斯特频率不同，
落进"4–10kHz"这个窗口的分量根本不是一回事。

同域重测（都在同一采样率下）才发现，40kHz 的成品原样是 0.963，
所谓"降了 6%"完全是跨域比较的假象。

### 留下的教训

**指标对比必须在同一条件下做。** 采样率、时长、响度，任何一项不一致，
比较结果就没有意义。而且这种错误特别隐蔽——数字看起来很有说服力。

后来我还犯过一次同类错误：把"原始混音"和"分离后的人声"的指标直接比，
忽略了后者去掉了伴奏，高频占比自然不同。

## 五、搜《群青》出来《群青信号》

### 现象

用户点歌"群青"，机器人放了一首《群青信号》。这是另一首歌。

### 原因

筛选逻辑只判断**标题里包含歌名**。而"群青信号"包含"群青"，
并且它时长更短，按"短的优先"排到了前面。

### 修复过程（试错了两次）

第一次我想的解法是"剥掉标题里的出处和翻唱标记，看剩下的是不是正好等于歌名"。
写了个正则去反复剥，结果被贪婪匹配坑了——
`翻唱` 这个词会被 `唱` 抢先匹配掉，"天童爱丽丝翻唱 群青YOASOBI"
因此判否，把本来正确的候选也排除了。

第二次换成**直接看歌名后面那个字**：

- 后面没字，或者跟着原唱名字（`群青YOASOBI`）-> 是这首歌
- 后面跟着"信号""的""之""版""号"这类字 -> 是另一首

简单得多，也不会因为标题多一个标记就失效。

同一轮还发现两个附带问题：

- 时长上限设成了 240 秒，导致《群青》的**全部**候选（246–260 秒）
  都被排除，表现为"未找到"。放宽到 420 秒就好了，反正只截 30 秒。
- 要求标题必须含"翻唱"两个字，把《AI爱丽丝-群青》这种正经标题排除了。

改完之后实测 14 首歌，命中从 4 首变成 10 首，而且选中的都是对的那首。
没命中的确实是搜不到对应翻唱。

## 六、30 秒的请求产出 195 秒的成品

### 现象

用户点了一首 30 秒的片段，成品却是 195 秒。

### 原因

流水线里 `stage_separate` 和 `stage_convert` 用了**同一个 tag**，
于是 UVR5 的中间目录是同一个：

```
stems\sing_<BV>_HP2_all_vocals\vocal_sing_<BV>.wav_10.wav
```

同一首歌先跑整首、再跑 30 秒片段时，两者写同名文件。
而 UVR5 见到同名文件就**跳过重算**，所以转换阶段读到的
是上一轮整首歌的干声。

清理前那个目录里确实躺着三个互相覆盖的 vocal：195.79 / 55.00 / 30.00 秒。

### 修复

两处：

1. tag 带上输入时长（`<标签>_<秒数>`），不同输入永不撞名；
2. `stage_convert.py` 增加**输出时长与输入一致性校验**（容差 2 秒）。

第二条是关键。"读错输入文件"产生的是**合法音频**，
前面那些"是不是有效音频"的检查全都抓不到它。

### 顺带修掉的拼接 bug

分段转换的拼接逻辑，第一版把重叠区**整段拼了上去**，
导致 195.79 秒的输入产出 200.72 秒。改成"每段只贡献新增部分"之后，
195.79 -> 195.52 秒，差 0.14%，是逐段整数取整的累积。

## 七、测试号称零依赖，其实不是

### 现象

用项目自己的 venv（干净环境）跑测试，失败了：

```
ERROR: tests.test_ffmpeg (unittest.loader._FailedTest)
ERROR: test_cq_path_is_absolute (tests.test_v4_media.MediaCQTest)
```

### 两个原因

**第一个**：`tests/test_ffmpeg.py` 顶层写了 `import numpy`。
在干净环境里这会**导致整个文件收集失败**，
报错是"test_ffmpeg 加载不出来"，而不是清晰的"缺 numpy"。

我在添加"用真实音频验证切段位置"那条用例时引入的。
修法是改成可选导入，无依赖时跳过那一条：

```python
try:
    import numpy as np
except ImportError:
    np = None
HAS_AUDIO_LIBS = np is not None and sf is not None

@unittest.skipUnless(HAS_AUDIO_LIBS, NO_AUDIO_LIBS)
def test_seek_lands_at_the_right_place(self):
```

零依赖环境跳过 1 条，装了依赖的环境仍然完整跑 36 条。

**第二个**：`tests/test_v4_media.py` 从适配层导入 `_media_cq`，
而适配层整块包在 `if HAS_NONEBOT` 里，且模块顶层会调用 `get_driver()`，
于是报 `ValueError: NoneBot has not been initialized`。

这个尤其值得记：项目自己在 `tests/test_media_capture.py` 的模块说明里
**早就写过这个教训**——"逻辑放在 aliceqq.media 而不是适配层，
就是为了能被这里测到"。我写新测试的时候违反了它。

修法不是加 try/except，而是**把 `_media_cq` 的逻辑搬回核心包**
（`aliceqq.media.cq_code_for`），适配层只做转发。

### 为什么一直没发现

我一直在开发机上跑测试，那台机器装了 numpy、nonebot、torch，什么都有。

**换到干净目录才知道。**

从那以后，交付前换个空目录 clone 一次跑 `--setup` 成了固定动作。
上面七条里，至少三条是这么发现的。

## 八、`.env.example` 里的重复键

### 现象

用户在干净目录生成 `.env` 之后，项目自检报出 `.env` 里有 8 个重复键。

### 原因

`.env.example` 里有**三段**重复的 TTS 配置，而且值互相冲突：

```
TTS_VC_BLEND=alice_ja:0.7,alice_zh:0.3      <- 第一段给了值
TTS_VC_BLEND=                                <- 第三段给了空值，覆盖了上面
```

空值静默覆盖了真实值，导致"混合音色怎么调都不生效"。

### 为什么它能藏这么久

**项目自检只检查了 `.env`**，而 `.env` 不入库、每个人不同。
模板本身从来没被检查过。

修法不只是合并那三段，更重要的是**把 `.env.example` 也纳入自检**。
这样以后不会再复发。

### 同类问题

我之前在别处也踩过一模一样的坑：`.env` 末尾一个空的 `TTS_VC_BLEND`
静默覆盖了上面设置的值。"重复键会静默覆盖"这件事，
在这个项目里出现过两次。

现在的 `scripts/env审计.py` 专门查这个，自检里也会跑。

## 九、代理挂了，但报错指向 GitHub

### 现象

推送代码时：

```
浏览器  Failed to load resource: net::ERR_CONNECTION_RESET
git     Recv failure: Connection was reset
```

看起来像 GitHub 被墙、或者认证失败、或者仓库不存在。

### 排查

我先去测网络。用 Python 的 requests 探测，**GitHub 完全能连**：

```
github.com        经代理 HTTP 200
api.github.com    经代理 HTTP 200
```

那就奇怪了——同样的机器，为什么浏览器和 git 不行？

再查代理端口：

```
Get-NetTCPConnection -LocalPort 11808 -State Listen   # 空
Get-Process xray                                      # 进程已不在
```

**代理客户端挂了，但 Windows 的系统代理设置仍然指向那个端口。**

所有走系统代理的程序都会把流量发到一个死端口，于是被重置。
而它们自己完全看不出是代理没了。

### 留下的教训

这个故障最坑的地方是**它看起来像外部服务的问题**。
而且多个程序**同时**失效——浏览器和 git 一起坏。

如果只是 GitHub 被墙，不至于连认证弹窗都打不开。
这个"同时"本身就是线索。

后来我把它做成了 `scripts/推送GitHub.py` 的第 0 步：
先探测系统代理指向的端口有没有程序在监听，不可用就直接停下并说明，
不让后面的步骤报一堆误导性的错。

### 后续：环境会变

同一个问题，后来还反转过一次：

| 时刻 | 直连 | 代理 |
|---|---|---|
| 第一次 | 通 | 挂了 |
| 第二次 | 不通 | 通 |

两次的报错几乎一样（`Connection was reset`），但处理方法完全相反。
所以现在那个脚本会**先探测再决定**走哪条路，
而不是固定配一个代理。

## 十、GitHub 不会因为 push 自动创建仓库

我一直以为 `git push` 到一个不存在的仓库时，GitHub 会自动创建它。
实测：

```
认证成功 -> remote: Repository not found.
```

**没有自动创建。** 这个便利功能取决于凭据类型和账号设置，不能依赖。

正确做法是先在网页上建空仓库——**不勾 README、不勾 .gitignore、不选 license**，
因为本地已经有提交了，加任何初始文件都会造成历史冲突。
