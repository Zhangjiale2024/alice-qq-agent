# Alice QQ Agent

一个面向真实消息平台的可控多模态 Agent。

它可以理解用户发来的图片，根据消息决定是否调用工具，查询最新信息，
保存用户主动要求记住的内容，也会在操作失败时直接说明失败原因。

目前有 943 项离线测试。核心逻辑约 16,000 行，不依赖第三方 Python 包。

## 现在能做什么

最初只是想做一个能在 QQ 上聊天的机器人。后来发现，聊天里有几件事不能只靠模型自己说：

- 用户发来一张图，确实要看懂上面是什么；
- 用户说了一段语音，确实要听清他说了什么；
- 用户说“记住这个”，确实要写进数据库；
- 用户问最新活动，确实要查资料；
- 群里出现广告，至少要先判断是否符合规则；
- 语音、撤回、禁言等操作，做没做必须和实际结果一致。

所以项目里把这些能力拆成了工具，由模型根据上下文决定是否调用。

| 工具 | 用途 |
|---|---|
| `remember` | 保存用户明确要求记住的信息 |
| `web_search` | 查询活动、价格、规则等时效性信息 |
| `academic_search` | 查询论文，使用 CrossRef、Semantic Scholar 和 arXiv |

模型调用工具后，执行结果会以 `role=tool` 的形式放回对话，再让模型根据真实结果生成回复。

例如，用户说：

```text
帮我记住，我不吃香菜
```

模型决定调用 `remember`，工具执行成功后，才会回复：

```text
已记录。以后点菜时我会帮你避开香菜。
```

这句话不是只由模型口头承诺，背后确实完成了一次写库。

## 语音理解

用户发来的语音会被真的识别成文字，再交给模型。

这块以前也是断的，而且断得更彻底：\sr.py\ 早就有识别能力，
但它只被用在「转写 B 站视频音轨」上。用户直接发来的语音消息
在适配层就没被抽出来，模型收到的是一条空文本，表现就是
「发语音它不回」或者「回一句莫名其妙的话」。

实测一条 3 秒的语音（TTS 合成，内容是「爱丽丝今天想去打游戏」）：

\\	ext
识别耗时   3.7 秒（本地 faster-whisper，不联网不花钱）
转写结果   艾利斯今天想去打游戏。
模型回复   爱丽丝，收到小星的语音了！打游戏……这个任务爱丽丝很喜欢。
           不过爱丽丝先确认一下：小星是想现在出门去街机厅打，
           还是想在家/线上联机打？
\
走的是配置里已有的 ASR 后端，支持云端 OpenAI 兼容接口和本地
\aster-whisper\ 两种：

\\ash
ASR_ENABLED=1
ASR_PROVIDER=local          # 或 openai_compatible
ASR_LOCAL_MODEL=small
\
几个刻意的处理：

**识别结果要带上质量警告。** ASR 在噪声和背景音乐上会输出
「通顺但完全错误」的文本，光看文字看不出来。项目里本来就有
\quality_warning()\ 判断这种情况，这里必须用上——否则等于把
错误信息当成用户原话交给模型。

**听不到就说听不到。** 没有 ASR、额度不足、识别失败时，
提示词里会注入「你没有听到内容」，并要求模型如实说明、
**不要猜他说了什么**。

**额度独立。** 「转写视频音轨」和「听用户说一句话」用量级完全不同
（前者一天几次，后者可能几十次），共用额度会导致转两段视频
就把语音对话的额度吃光，所以分成了两项。

**识别质量是量过的，不是凭感觉。** 用 12 条已知文本的语音做基准，
本地 whisper small 的字符错误率：

`	ext
不加提示                    40.6%   完全正确  0/12
加「请用简体中文转写」        15.9%   完全正确  5/12
再加角色专名                 1.0%   完全正确 11/12
`

关键发现是**主导错误其实是输出繁体字**（「今天天气看起来还不错」->
「今天天氣看起來還不錯」），不是同音字。所以提示词里指定简体
贡献了大部分改善，列上角色专名把剩下的也压下去了。

三个被实测否掉的想法（记下来免得以后重走）：
事后做简繁转换（7.0%，不如直接提示的 1.0%）、
	emperature=0（40.6%，完全没用）、
自己写代码把阿拉伯数字转汉字（把「10点」改成了「一零点」，
逐字替换不懂量级；在提示词里说一句就够了）。
**同音字会错，这是已知的。** 实测 \small\ 模型把「爱丽丝」识别成
「艾利斯」。这类同音错误目前靠模型结合上下文自行理解，
没有做专门的角色名词典纠正。

## 图片理解

用户发来的图片会真的送到视觉模型去看，识别结果注入对话上下文。

这一块以前是缺的：适配层只取了 `get_plaintext()`，图片段既不进文本也不进
别的字段，所以模型看不到图，只能靠文件名和用户的话去猜。
`Message` 的类型注解是 `Dict[str, str]`，也装不下多模态消息的 `content` 数组。

现在支持的链路是：

```text
QQ 的 image 段
  -> 适配层抽成 ImageRef（带 url 或本地路径）
  -> IncomingMessage.images
  -> 引擎调视觉模型（OpenAI 兼容的 image_url 协议）
  -> 识别结果注入系统提示词
  -> 模型据此回应
```

走的是 OpenAI 兼容的视觉接口，**不绑定厂商**——
`qwen-vl`、`glm-4v`、`kimi`、本地 ollama 都是同一个协议：

```bash
VISION_ENABLED=1
VISION_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
VISION_API_KEY=sk-xxx
VISION_MODEL=qwen3-vl-plus
```

几个刻意的设计：

**它是"感知"步骤，不是工具。** 工具是模型自己决定要不要调的，
但"用户发了图"是事实——模型没法决定不看。所以视觉结果直接注入上下文，
而不是挂成一个 `describe_image` 工具等模型来调。

**看不到也要说出来。** 没配视觉模型、额度不足、识别失败时，
提示词里会注入一段"你这次没有看到图片内容"，并明确要求模型
如实告诉用户、**不要猜图里是什么**。不注入的话，模型会以为没图这回事，
转而根据用户的话编一个画面出来。

**按张独立计额度。** 和"生成图片"是两件事，额度分开算，
一次最多看 3 张（群聊里连发多图很常见，不设上限成本会翻倍）。

**不串轮。** 上一轮的图片描述不会带到下一轮——
把 A 发的图描述给 B 看就是泄漏内容。这条有专门的测试守着。

使用 `--trace` 可以查看这条链路：

```text
决策      replied
模型      openai / deepseek-chat
工具目录  remember✓ web_search✓ academic_search✓
①         模型决定调用 remember
②         执行结果：成功，已记录
③         将工具结果回灌给模型
记忆落库  2 条
```

## 视频理解

用户发来的视频会被拆成**画面**和**声音**两部分，分别交给已有的两条链路：

```text
视频 --抽帧--> JPEG --+--> 视觉模型（图片理解那条）
     --抽音轨--> WAV --+--> ASR（语音理解那条）
```

这样做的好处是视频**不需要新的模型、新的额度、新的护栏**——
图片和语音那两套门禁与"看不到就说看不到"的护栏自动生效。

实测一段 3 秒的视频（深蓝底 + 白字 + 音轨说话）：

```text
debug.video = {ok: True, frames: 3, frames_ok: True,
               has_audio: True, transcript_chars: 10, elapsed: 11.53}

注入提示词
  【画面】纯深蓝色背景，左下角有一行白色文字："ALICE VIDEO 5570"
  【声音】音轨转写：這是愛麗絲的測試視頻

模型回复
  "爱丽丝看到了！从机器抽出来的几帧画面看——
   画面部分：纯深蓝色背景，左下角有一行白色文字「ALICE VIDEO 5570」…
   声音部分：音轨转写出来是「這是愛麗絲的測試視頻」。"
```

模型**主动区分了两个来源**，没有假装自己看过整段视频——
提示词里明确要求了这一点，因为"我没看过全片"这件事
它自己不会知道。

几个边界情况都当成一等情况处理：

- **没有音轨不是错误。** 纯画面视频很常见，抽帧照样能用。
- **抽不出帧但有声音仍然算成功。** "有人说话"值得听。
- **长视频只转写前 120 秒。** 又慢又贵，而且开场通常已含主要信息。
- **抽帧缩到 640 宽。** 视觉接口按图算钱，1080p 一帧好几 MB，
  缩完通常几十 KB，对"看懂发生了什么"完全够用。

## 多轮工具编排

模型可以连续调用多个工具，而不是只调一个就结束。

比如"记住我在做一个 LLM Agent 项目，顺便查一下 ReAct 的论文"，
它会先调 `remember`，拿到结果后再调 `academic_search`，最后组织回复：

```text
模型调用次数   3
工具循环轮数   2
用到的工具     ["remember", "academic_search"]
```

三条约束：

**轮数上限默认 3。** 模型可能一直调工具不出结论。撞上限时如实说明
"查了几轮还没理清楚"，不假装答完了。

**完全相同的调用不重复执行。** 带不同参数不算重复（先查 A 的论文
再查 B 的是正当用法），但同一个调用再来一次只会浪费额度，
而且往往意味着模型在绕圈。这种调用会回灌一条"刚刚已经执行过了"，
否则模型会以为是失败而重试。

**中途失败不再静默。** 以前那一步套着 `except LLMError: pass`，
失败了什么也不说；现在会把原因记下来并用已有结果组织回复。

## 检索方式

项目保留两种检索路径。

第一种是模型自己调用 `web_search`。第二种是引擎先判断消息是否涉及最新信息，如果涉及，就先查资料，再把结果交给模型。

保留第二种路径是因为实际测试中，角色扮演模式下的模型有时更愿意顺着角色说话，而不是主动调用工具。用户问“今天有什么活动”时，不能因为模型没有调工具就直接凭记忆回答。

示例：

```text
检索路径  引擎判断为先检索
检索      provider=bilibili ok=True 条数=6 耗时=5.1
```

## 几个硬性限制

模型最容易造成的问题，不一定是回答内容错误，而是把没有发生的操作说成已经发生。

目前有几类情况由代码直接处理：

- 回复中出现“语音已经发给你了”，但实际没有附件时，删除这类表述并改为说明失败；
- 用户要求保存身份证号等敏感信息时，由 `looks_sensitive()` 拦截写入；
- 撤回、禁言等管理动作失败时，把实际错误返回给管理员，不让模型自行补一句“操作成功”。

这些规则不依赖模型自觉，换模型也有效。

```bash
python -m unittest discover -s tests -t .
python -m aliceqq --test-plan
```

三类测试覆盖范围不同：

|---|---|---|---|
| 离线测试 | 无 | 模式隔离、限流、护栏、工具分发等逻辑 | 回复是否自然、QQ 是否收到消息 |

目前第三层还没有充分验证。

CI 在 Ubuntu 和 Windows 上运行，覆盖两个 Python 版本，并且故意不安装核心依赖。这样可以确认“核心逻辑零第三方依赖”不是文档上的描述，而是每次提交都会检查的状态。

## 运行

初始化环境：

```bash
python -m aliceqq --setup
```

不需要 QQ 或 API Key，也可以先本地运行：

```bash
python -m aliceqq --demo
python -m aliceqq --repl
python -m aliceqq --show-prompt "你好"
```

接入真实模型前，在 `.env` 中填写 `LLM_API_KEY`：

```bash
python -m aliceqq "帮我记住我喜欢明日方舟" --live --trace
```

接入 QQ：

```bash
python -m aliceqq --serve
```

该模式需要 NoneBot2 和 NapCat。

## 代码结构

```text
aliceqq/
  engine.py
  tools.py
  llm.py
  memory.py
  search.py
  academic.py
  moderation.py
  media.py
  singing.py
  adapters/
    nonebot_plugin_alice.py

integrations/
  nonebot/
    run.py
```

`aliceqq/` 目录不直接导入第三方库。

- `engine.py`：组装上下文、请求模型、执行工具、运行护栏；
- `tools.py`：工具注册和 OpenAI 格式 schema；
- `llm.py`：使用 `urllib` 实现的 OpenAI 兼容客户端；
- `adapters/`：把 QQ/NoneBot 事件转换成内部格式；
- `integrations/`：负责启动真实 QQ 接入。

第三方能力采用延迟导入。例如没有安装 `faster-whisper` 时，语音识别会返回不可用，其他功能仍然可以运行。

这样做主要是为了：

1. 核心测试可以完全离线运行；
2. 更换消息协议时只需要修改适配层；
3. 只安装 Python 也能运行本地演示。

## 质量基准

多模态理解的准确率是**量过的**，不是感觉。实测数字与被数据否掉的
方案记录在 [docs/多模态质量基准.md](docs/多模态质量基准.md)。

```text
语音识别   字符错误率 40.6% -> 1.0%（12 条基准，本地 whisper small）
图片理解   18/18 读对（含重度退化），关键事实命中 14/14，编造 0 次
```

**图片那个数字要连范围一起看。** 18 张图都是我自己合成的，
所以能说的是"合成图上可靠"，包括这些退化：字号小到 10px、
29 字符长编号、形近字符 `0O1lI5S2Z`、以及
"复杂背景 + 噪点 + 旋转 10° + 模糊 + 低对比 + 13px 小字"叠在一起。

**没测过**的：真实照片（自然场景、光照、遮挡）、
表情包和梗图（要判断"主体是什么"而不只是抄文字）、
几十行小字的长截图。这三类都需要真实素材，
而**不能用网上的照片做基准**——那是拿别人的人脸当测试数据。

所以"图片理解可用"这句话的准确范围是：**合成图上可靠，真实素材未测**。

## 踩过的坑

详细记录在 [docs/踩坑记录.md](docs/踩坑记录.md)，这里只列几个实际遇到的问题。

| 现象 | 原因 |
|---|---|
| 工具始终不调用 | 请求模型时漏传了 `tools` 参数 |
| 语音发送失败 | 文本中混有英文，服务端缺少 `nltk` 资源并返回 HTTP 400 |
| 长音频转换崩溃 `0xC0000005` | Windows 页面文件被其他程序占满 |
| 高频指标下降 6% | 直接比较 44.1kHz 源文件和 40kHz 成品，结果没有意义 |
| 搜索《群青》得到《群青信号》 | 只做标题包含判断，没有区分完整歌名 |
| 30 秒请求生成 195 秒音频 | 中间文件重名，UVR5 跳过了重新处理 |
| “零依赖”测试在干净环境失败 | `test_ffmpeg` 顶层导入了 `numpy` |

这里有几个经验比较值得记下来：

“没有报错”不代表操作成功。Windows 的 `0xC0000005` 这类退出码，需要看进程级结果，不能只看 Python 异常。

各模块单独正确，也不代表整条链路接通。工具注册表、schema、执行器和回灌逻辑都没问题，但少传一个参数，工具就会完全失效。

本机环境过于完整也会掩盖问题。现在交付前会在干净目录重新运行一次 `--setup`。


会检查：

## 常见问题

### 在 cmd 中使用 `rm .env`

`rm` 是 Linux 和 macOS 的命令。Windows 下使用：

```bash
python scripts\重置配置.py
```

### 修改配置后没有生效

先检查是否有重复键：

```bash
python scripts\env审计.py .env
```

后出现的配置可能会覆盖前面的同名配置。

### `--serve` 提示缺少 NoneBot2

只有接入真实 QQ 时才需要它。运行 `--setup` 会自动安装。

如果只是本地测试，可以直接运行：

```bash
python -m aliceqq --repl
```

### 机器人不回复

先运行：

```bash
python scripts\链路体检.py
```

它可以帮助区分：

- 反向 WebSocket 没有连接；

## 目前还没有解决的问题

1. QQ 适配层还没有在真实设备上充分验证。媒体发送和群管理动作需要真实 QQ 环境，目前没有完整的自动化测试。
2. 暂时没有完整的多轮工具编排。工具结果回灌后最多再请求一次模型，还不是完整的 ReAct 循环。
3. 反广告目前使用规则匹配，不是模型判断。优点是可解释，缺点是容易漏掉变形广告。
4. 唱歌链路只有意图识别和缓存测试，完整流程还没有自动化覆盖。
5. 当前是单进程部署，数据使用 SQLite。多实例部署需要改用共享存储。
